# QQ 桥接第三代仿真引擎（Gen3）设计方案

> 状态：设计稿（2026-10 快照）。`reserved3` 已落地，实现说明以 [GEN3.md](GEN3.md) 与代码为准；
> 本文保留当时的完整设计与取舍，其中部分内容（如 `qq-chat-root`、部分阶段）仍未落地。
> 基线：`reserved2` / `qq-chat-v2`  
> 目标：在**完整保留二代全部能力**的前提下，把二代从「会调用工具的聊天机器人」升级为「有连续关系、情景记忆、发言判断、表达时机和更多社交动作的群成员」。  
> 一句话：二代解决“能不能自主收发”，三代解决“像不像一个具体的人，在这个群里，和这些人，处在这个时间点”。

---

## 0. 先给结论

三代的重点不是再加十几个工具，而是补五层二代没有的东西：

1. **关系层**：对不同 QQ 号有稳定、可解释、可编辑的态度差异，而不只是“管理员/群友”两种标签。
2. **情景记忆层**：每次唤醒都知道“我睡着这段时间群里发生了什么、谁找过我、我答应过什么”，且不依赖 DSH 会话是否被重置。
3. **判断层**：把「唤醒」和「回复」拆开。@ 只是高优先级信号，不是必须回复；发言有预算、有让位、有已读不回。
4. **表达层**：回复延迟、长度、分条、错字、改口、撤回、正在输入，由“人味模型”控制，而不是调用工具后立刻发送。
5. **动作层**：发图、语音转写、文档阅读、消息表情回应、群签到/点赞/资料卡、分享卡片等真人会做的社交动作。

这五层做出来，1/2/3/5/6/7 会一起改善；第 4 点（token）靠“上下文编译器 + 静态前缀瘦身 + 一次取齐”解决；第 8 点（二代功能全保留）用“新三代模式 + 二代原样保留”解决；第 9 点（owner 私聊不好控制）用会话树解决。

另外要加一个**横切的控制面：会话树（树干 / 树枝）**。现在 owner 私聊和普通群聊是平级的，owner 想看别的群、想给别的群下命令，只能靠零散的跨会话工具；三代把 owner 私聊明确成“树干”，其他会话是“树枝”：树枝之间互不可见，树枝只能向上送摘要/告警，树干可以向下看摘要、发命令。详见 6.7 节。

### 问题 → 方案速查

| 要解决的问题 | 主要对应模块 | 一句话做法 |
|---|---|---|
| 1. @ 就回答、话太多 | L1 感知 + L3 判断 | @ 分 summon/social/mass；回复压力 + 预算 + 让位 + 冷启动延迟 |
| 2. 唤醒不知道上下文 | L2 记忆 + 上下文编译器 | 独立于 DSH 的情景摘要 + 当前线程 + 待办 + 重置 recap |
| 3. 对群友的印象功能弱 | L2 关系 | QQ 号主键的人物卡：事实/事件/边界/证据/语气矩阵，只注入相关 3~5 人 |
| 4. token 效率 | 第 10 节 | 先测 cache hit；上下文编译、静态前缀瘦身、`qq_context` 一次取齐、异步便宜模型 |
| 5. AI 感重、时间固定、无差别 | L4 表达 | 延迟模型 + outbox + 正在输入 + 关系语气 + 可用性状态 + 受控的不完美 |
| 6. 互动不够 | L4 动作 | 发图、表情回应、语音转写、OCR/文档、梗图、撤回改口、历史搜索、签到/点赞 |
| 7. 更像人 | 全部 | 感知→记忆→判断→表达→反思的闭环，而不是单点功能 |
| 8. 二代能力全保留 | 第 20 节 | 新增 `reserved3`，`reserved2` 原样保留；42 个工具逐个冒烟验收 |
| 9. owner 私聊和普通会话平级、不好控制 | 6.7 会话树 | owner 私聊 = 树干（只看摘要/发命令）；其他会话 = 树枝（互不可见，只能上报告警） |

## 1. 现状诊断：九个问题分别卡在哪

| # | 现象 | 直接原因（代码/配置） | 更深层原因 |
|---|---|---|---|
| 1 | 只要 @ 就回答，话太多 | `evaluateWakeTriggerV2` 中 `tr.atMention` 命中即返回 `atMention`；`qq-chat-v2` persona 写“被 @ 或直接提问必须回”；桥接发送上限默认 60 条/小时，约束太松 | 把“唤醒”当成“必须回复”，没有回复预算、让位和“已读不回” |
| 2 | 唤醒时不知道之前上下文 | `buildWakeSnapshotV2` 最多 12 条未读 + 4 条最近、6000 字符；unread 缓冲有上限，旧消息会被挤掉；`buildWakePromptV2` 只给最近一条 30 字摘要；DSH 会话在模式/preset/白名单变化时退役重建，历史丢失；compaction 也会裁掉旧内容 | 记忆是“消息缓冲”，不是“事件摘要”；没有独立于 DSH 会话的持久记忆 |
| 3 | “对群友的印象”很弱 | `memberImpressions` 以**显示名**为 key，只有 `traits[] + interactionCount + lastSeenAt`；`formatMemoryV2` 只注入最近 10 人；没有证据、时间、情感、关系、场景；不能编辑单条事实 | 印象只是“形容词标签”，没有变成可执行的语气、称呼、话题、边界和回复速度 |
| 4 | token 效率不够 | `qq-chat-v2` prefix 约 9,830 字符；42 个 MCP 工具的主描述合计约 6,645 字符（还不含参数说明）；唤醒 prompt 里静态段重复；快照上限 6000 字符；一轮常调用 3~5 次读工具；工具结果全量 JSON | 没有上下文编译器，所有能塞的东西都塞；没有“按需展开”和“预算降级” |
| 5 | AI 感重：回复时间固定、对账号无差异 | `sendMessagesV2` 在工具调用后立即发送；`computeGapsV2` 只算多条消息之间的间隔，第一条没有延迟；同一套 persona 对 owner 和普通群友；没有可用性/精力/心情；没有错字、改口、撤回、漏看 | 只有“表达内容”模型，没有“表达时机、关系、状态”模型 |
| 6 | 互动能力不够 | 目前只能发文字/表情包/语音（默认关），不能发图片；收到语音只显示占位文本；不能读群文件/文档；没有消息表情回应、正在输入、群签到/点赞/资料卡、分享卡片；也没有面向模型自己的“撤回/改口”（现有 `qq_admin` 的 `recallMessage` 是管理员动作，不是自然表达） | 工具面偏“收发文本 + 表情”，缺少真人日常的社交动作 |
| 7 | 整体还是不够像人 | 以上因素叠加；没有“人味”指标，也没有盲评机制 | 缺少统一的社会认知循环：感知 → 记忆 → 判断 → 表达 → 反思 |
| 8 | 三代必须包含二代全部能力 | 二代有 42 个工具、WakeConfig、预睡眠观察、记忆、表情、语音、跨会话、管理员动作、控制台 | 不能破坏性替换；必须新老并存、可回退、逐项验收 |
| 9 | owner 私聊和普通会话平级，不好控制 | `private:<ownerQQ>` 和其他会话一样走 `state.sessions` / `qq-chat-v2`；跨会话能力散在 `crossSessionSend` / `crossSessionDelegate` / `crossSessionControl` / `qq_delegate` / `/mute`；没有分支列表、分支摘要、上报 inbox、统一命令总线 | 缺少“树干/树枝”的控制面层级；owner 私聊只是另一个聊天窗口 |

### 1.1 一个关键判断

二代的问题不是“模型不够聪明”，而是**桥接给模型的信息结构和决策结构太扁平**：

- 它知道“有人 @ 我”，但不知道“这个 @ 是玩笑、是召唤、还是 @ 所有人”；
- 它知道“有 12 条未读”，但不知道“我离开的 3 小时里群里聊了什么、谁问过我、我答应过谁”；
- 它知道“张三互动 3 次”，但不知道“张三不喜欢被催、上次聊考研、我该叫他三哥”；
- 它知道“该发消息”，但不知道“现在几点、我刚说过几句、对方是不是正在跟别人说话、我该等 8 秒还是 40 秒”；
- 它知道“发文字/表情”，但不知道“真人这时候可能只回一个表情、发张图、或者干脆不回”。

三代就是把这几件事补上。

## 2. 设计目标与非目标

### 2.1 可量化目标

| 指标 | 二代现状（估） | 三代目标 |
|---|---|---|
| @ 后的回复率 | 接近 100% | 60~80%；owner/直接提问 >90% |
| 每轮发送条数 | 2~3 条 | 1.0~1.8 条 |
| 连续 bot 发言（无人接） | 可能 3+ 条 | ≤2 条，硬上限 |
| 首回复延迟 | 约等于模型生成时间，较固定 | 中位数 4~12s，p90 20~40s，方差明显 |
| 唤醒上下文 | 最多 12 未读 + 4 最近 | 规则摘要 + 快照已实现；人物卡/线程/24h LLM 摘要待后续 |
| 会话重置后的上下文 | 基本丢失 | 500~800 字 recap 恢复 |
| 活跃群友关系卡覆盖 | 仅被记录过的显示名 | ≥80% 活跃群友，按 QQ 号 |
| 每轮注入人物卡 | 最近 10 人 | 只注入 3~5 个与当前对话相关的人 |
| 可控上下文体积 | 约 2.5~3 万字符量级 | 降到 1.5~2 万字符，降 30~40% |
| 每轮工具调用次数 | 3~5 次 | 1~2 次（`qq_context` 一次取齐） |
| 每日 / 每 2 小时限额 | 只有每分钟 / 每小时 | 分支级 + 全局级已实现；控制台可改；超限 429 或延后；重启不丢 |
| 树干概览 | 无（owner 私聊与普通会话平级） | `/branches` 3 秒内返回，每分支 1 行、≤120 字符 |
| 树枝隔离 | 无明确保证 | 树枝读不到树干/其他树枝；跨群事实 0 泄漏 |
| 盲评“像人” | 基线 | 提升 ≥0.8/5，安全回归 0 失败 |

### 2.2 非目标

- **不冒充真人**：不主动声称自己是真人，不伪造线下经历；被直接问到时按既定人设回答（DeepSeek 鲸鱼形象）。拟人化只用于节奏、记忆、选择性和关系差异。
- **不碰钱**：红包、转账、支付一律不做。
- **不做破坏性管理**：踢人、禁言、拉群、加好友、批量私聊不做；管理员动作仍走现有确认机制。
- **不降低安全边界**：关系数据不参与权限判定；权限仍只看 ownerQQ、白名单、会话令牌。
- **不做平台规避**：不绕风控、不批量养号、不做自动化营销。

## 3. 设计原则

1. **二代是基线，三代是超集**：`reserved2` 原样保留，新增 `reserved3`；任何三代能力都能关掉回退到二代行为。
2. **唤醒 ≠ 回复**：唤醒只负责“让模型知道”，回复由判断层决定；模型可以选择回、短回、只回表情、等、不回。
3. **关系要可执行、有证据、可编辑**：每条印象都要有来源（哪条消息、什么时候），owner 能在控制台改/删；没有证据的形容词不进 prompt。
4. **记忆分层，摘要优先**：原文只保留最近窗口；更早的内容变成摘要、事实、关系事件；不靠无限堆上下文。
5. **预算是硬约束**：token、发言条数、唤醒次数、社交动作频率都有上限；模型可以“想多说”，桥接会拦。
6. **先测量后优化**：token 优化先看 cache hit、每轮输入构成，再决定砍哪里；不盲目删 prompt。
7. **像人不是装人**：自然来自于“会选择、会漏看、会迟到、会记得、会区别对待”，不是靠错别字堆出来的。
8. **所有新动作可审计、可关闭**：新工具默认最小权限，敏感动作默认关，owner 可查日志。

## 5. L1 感知层

### 5.1 每条消息提取什么

| 字段 | 取值 | 用途 |
|---|---|---|
| `speakerId` | QQ 号 | 关系主键，不能用昵称 |
| `speakerRole` | owner / admin / member / newbie / stranger | 语气与权限边界 |
| `directness` | `at_self` / `quote_self` / `name_self` / `question_to_me` / `question_to_group` / `statement` | 回复压力 |
| `addressee` | `me` / `other` / `all` / `unknown` | 防止抢话 |
| `mentionClass` | `summon` / `social` / `mass` | 唤醒时机 |
| `urgency` | 0~1 | “在吗/回我/急/等你”等 |
| `sentiment` | -1~1 | 心情、关系事件 |
| `intent` | 提问 / 请求 / 陈述 / 玩笑 / 挑衅 / 打招呼 / 告别 | 回复类型 |
| `threadId` | 引用链或时间窗 | 上下文归属 |
| `topic` | 关键词/向量 | 记忆检索 |
| `isRepeatMention` | 10 分钟内第 N 次 @ | 升级为 summon |

### 5.2 @ 分类：解决“只要 @ 就回答”的第一步

不是所有 @ 都值得立刻叫醒模型：

| 类型 | 判定 | 唤醒策略 | 回复压力 |
|---|---|---|---|
| `summon` | 直接提问/请求、owner、含“在吗/回我/急”、10 分钟内重复 @ | 立即唤醒 | 高 |
| `social` | 打招呼、玩笑、调侃、没有具体问题、群里正热 | 延迟 20~90 秒合批；若话题已翻篇则并入下次唤醒 | 中/低 |
| `mass` | @all、一次 @ 多人、群公告式 | 不立即唤醒，进摘要 | 低 |

实现上仍保留 `atMention` 触发，但把它拆成三个子原因：`atMention:summon`、`atMention:social`、`atMention:mass`。这样不会漏消息，也不会让每个 @ 都变成一个付费回合。

### 5.3 线程与“谁在跟谁说话”

- 用引用关系、回复关系、时间窗（90 秒）和话题相似度做轻量线程聚类。
- 线程状态：`active` / `cooling` / `ended`。
- 记录“当前线程的参与者”，用于判断“这句话是不是对大家说的”“是不是已经有人在答”。
- 不要求完美；先做到“同一个话题的连续消息归到一起”，就能显著减少抢话。

## 6. L2 记忆与关系层

### 6.1 四类记忆

| 类型 | 内容 | 存储 | 生命周期 |
|---|---|---|---|
| 工作记忆 | 当前一轮的消息、线程、临时判断 | 内存 | 一轮 |
| 情景记忆 | 一次会话/一段时间的摘要、事件、承诺 | `state/gen3/digests/` | 7 天，之后压缩进人物卡 |
| 语义记忆 | 关于人、话题、群的事实 | `state/gen3/people.json` | 长期，带证据与置信度 |
| 关系记忆 | 熟悉度、好感、信任、边界、互动统计 | `state/gen3/people.json` | 长期，带衰减 |

### 6.2 情景摘要（解决“唤醒时不知道上下文”）

每次唤醒不再只给“12 条未读 + 4 条最近”，而是给一个编译后的上下文包：

```
【你离开期间】
- 时间：21:03 → 23:41（2 小时 38 分钟），共 47 条，6 人说话。
- 主线：张三和李四在聊考研复试；王五发了一张成绩单截图；有人问“鲸鱼呢”。
- 与你有关：张三 21:20 @ 你问“你觉得调剂稳吗”，还没人答；李四 22:05 引用了你上周说的“先看排名”。
- 群氛围：热闹，偏焦虑，偶有玩笑。
- 你的待办：上周答应帮张三查调剂信息，还没做。
- 当前线程：张三、李四仍在聊，最后一条 3 分钟前。
```

生成方式：

1. **规则层**（同步，零 token）：消息计数、参与者、@ 我、引用我、问号句、时间跨度、最后一条。

#### 关系演化规则

- **熟悉度**：每次有来有回的互动 +1~2；单向搭话 +0.5；连续 7 天无互动每天 -0.5；上限 100。
- **好感**：被帮助/被认同 +2；被无故攻击 -2；玩笑互损不扣分；单条消息不翻盘，至少 3 条证据才明显变化。
- **信任**：稳定互动、守约、私聊过 +1；失约、泄露 -5；上限 100。
- **类型**：owner 固定；familiarity/affinity/trust 组合映射到熟人/常客/新人/陌生人；owner 可手动锁定。
- **衰减**：所有数值按天衰减，避免“三年前聊过一次”永久高熟悉。
- **证据**：每次变化记录 `sourceSeq`、时间、原因；控制台可查。

### 6.4 记忆检索

新增 `qq_memory_search(query, person?, days?)`：

- 输入：关键词/自然语言 + 可选人物 + 时间范围。
- 检索：人物卡事实、情景摘要、历史消息索引（桥接自己存的最近 N 天）。
- 输出：最多 5 条，带时间、来源、置信度；总字数 ≤600。
- 用途：有人说“上次那个”“你还记得吗”“之前说的”；模型不必靠猜。
- 兜底：检索不到就说“记不清了”，不要编。

### 6.5 记忆巩固与清理

- 异步任务，单并发，失败重试 1 次，不阻塞消息。
- 去重：同一事实多次出现只保留一条，更新置信度与最后确认时间。
- 冲突：新旧事实矛盾时保留新事实并标注“旧说法”，不要直接删。
- 过期：`ttl` 到期的事实转“历史”，不再注入；敏感信息默认 30 天。
- 容量：每人 facts ≤50、episodes ≤30；每群 digest ≤7 天；超出按时间淘汰。
- owner 控制台可查看、编辑、删除、导出/清空。

### 6.6 从二代迁移

- `memberImpressions` 是显示名 key：能匹配到 QQ 号的迁移；匹配不到的保留为 `alias-only` 卡片，等下一次该昵称发言时合并。
- 迁移不删除旧数据；`socialV2.json` 原样保留，三代只读复制。
- 迁移失败不影响启动；控制台显示“待合并的旧印象 N 条”。

### 6.7 会话树：树干、树枝与管理通道

> 这一节就是你说的“管理者账号是树干，普通会话是树枝”。它不是再加一个模式，而是给所有会话加一个**层级和控制面**。虽然放在 L2 后面，但它横切 L2/L3：既管“谁能看谁”，也管“谁能命令谁”。

#### 6.7.1 现状：为什么 owner 私聊“不好控制”

现在 `private:<ownerQQ>` 和普通群聊在桥接里是**同一种会话**：

- 都走 `state.sessions[key]`、都有独立的 DSH 会话、都用同一套 `qq-chat-v2`；
- owner 想看别的群，只能打开 DSH 控制台，或者在某个会话里用零散的 `qq_delegate` / `crossSessionSend`；
- 没有“所有分支的概览”，也没有“从 owner 私聊给某个群下命令”的统一入口；
- 树枝出了事（有人找 owner、群里吵起来、DSH 挂了）不会主动上报；
- 跨会话权限散在 `crossSessionSend` / `crossSessionDelegate` / `crossSessionControl` 和 `/mute` 里，语义不统一。

结果就是：owner 私聊只是“另一个聊天窗口”，不是“管理端”。

#### 6.7.2 三种角色

| 角色 | key | preset | 能力 | 不是什么 |
|---|---|---|---|---|
| **树干 root** | `private:<ownerQQ>` | `qq-chat-root` | 看分支概览/摘要；按需读脱敏原文；给分支下命令；收发 owner 消息 | 不是群成员；不参与群聊；不默认看到所有原始消息 |
| **树枝 branch** | 其他白名单 `group:*` / `private:*` | `qq-chat-v3` | 正常群聊/私聊；维护自己的摘要、记忆、唤醒、预算；可向上告警 | 不能读树干；不能读其他树枝；不能自己给其他树枝下命令 |
| **控制台 console** | 本地 Web | — | 与树干同级的最高权限；审计、配置、回放 | 不是 QQ 会话 |

**树干不是“更大的群聊”，它是控制面。** 它和树枝各自拥有独立的 DSH 会话、独立记忆命名空间、独立 agent token，互不共享上下文。

#### 6.7.3 五条硬规则

1. **树枝 → 树干**：只能送摘要/告警，不能送原始上下文；唯一通道是 `qq_escalate`。
2. **树枝 ↛ 树枝**：不能互相读；跨会话发送/委派只在 owner 触发时发生（沿用现有 `crossSessionSend` / `crossSessionDelegate`）。
3. **树干 → 树枝**：默认只看摘要；要看原文必须显式 `/read`，脱敏 + 审计；命令走 allowlist。
4. **owner 在群里的发言仍属于该树枝**：不因为说话的人是 owner 就把群升级成树干；树干权限只在 owner 私聊（`root.onlyPrivate=true`，已确认）。owner 在群里只能下“本分支”的管理命令，不能读别的分支，也不能 `/delegate`/`/broadcast` 到别的分支；要管别的群，回私聊。
5. **三个隔离**：DSH session 隔离、记忆 namespace 隔离、token 隔离。树干 token 不能用于树枝工具，树枝 token 不能用于 `qq_root`。

**树干的唤醒条件**（避免树干变成“另一个刷屏群”）：

1. owner 自己发消息；
2. `urgent` 告警（如有人明确找 owner、分支 DSH 故障、`/panic` 相关）；
3. 可选：每 2~4 小时一次的 digest（默认关，owner 可开）；
4. 普通 `info` / `attention` 只进 inbox，不唤醒；owner 下次说话时一起看。

#### 6.7.6 树干能看到什么：默认摘要，按需原文

| 层级 | 内容 | 上限 | 触发 |
|---|---|---|---|
| Dashboard | 每个分支 1 行：名称、状态、未读、最后活跃、headline | 10 个分支 / 1,500 字符 | 树干每次唤醒 |
| Summary | 分支 digest + 告警 | 400 字符 | owner 问“群里怎么样” / `/summary` |
| Raw | 最近消息（脱敏） | 20 条 / 1,500 字符 | 明确 `/read` 或“详细说说” |
| Why | 最近一次决策记录 | 200 字符 | `/why` |
| 不提供 | 分支系统提示、token、完整历史、其他分支原文 | — | 永不 |

**关键：树干默认不把分支原文放进 prompt（已确认）。** 它看的是“头条 + 摘要 + 告警”，只有 owner 明确要细节时才拉原文。这样树干几秒钟就能掌握 10 个群，而不是把 10 个群的聊天记录都塞进去。

#### 6.7.7 树干能下什么命令

| 命令 | 作用 | 是否需二次确认 |
|---|---|---|
| `/branches` | 列出所有分支与状态 | 否 |
| `/summary <key> [hours]` | 分支摘要 | 否 |
| `/read <key> [n]` | 最近 n 条（脱敏） | 否（但审计） |
| `/watch <key> on/off` | 订阅该分支告警 | 否 |
| `/mute <key> [minutes]` | 静音分支 | 否（owner 直接） |
| `/unmute <key>` | 恢复 | 否 |
| `/wake <key>` | 立即唤醒一次 | 否 |
| `/sleep <key> [minutes]` | 强制潜水 | 否 |
| `/pause <key>` / `/resume <key>` | 暂停/恢复分支 | 是（避免误停） |
| `/role <key> <角色>` | 改分支人格 | 是 |
| `/reset <key>` | 重置分支会话 | 是 |
| `/say <key> <text>` | 原样发一段 | 否（限频） |
| `/delegate <key> <instruction>` | 让分支用人设处理 | 否（优先用它） |
| `/broadcast <text>` | 向所有分支发同一段（高危） | 是 + 默认关 + 1 次/小时 + 最多 5 个分支 |
| `/why <key>` | 最近决策原因 | 否 |
| `/budget <key>` | 预算使用 | 否 |
| `/status` | 树干/分支健康 | 否 |

`/branches` 与 `/summary <群名或群号> [小时数]` 已在 2026-10-24 落地（只读、不经过模型）；其余命令待 Phase 1.5 的命令通道。

`/broadcast` 默认关；开启后仍需二次确认；1 次/小时、最多 5 个分支、≤500 字。树枝没有这个命令。

**命令作用域（已拍板）：树干能管所有分支，owner 在树枝里只能管当前分支。**

| 命令 | 树干（owner 私聊） | 树枝（owner 在群/私聊） |
|---|---|---|
| `/branches` | 全部 | 拒绝（看不到别的分支） |
| `/summary` | 任意分支 | 仅当前分支 |
| `/read` | 任意分支 | 仅当前分支 |
| `/mute` / `/unmute` | 任意分支 | 仅当前分支 |
| `/wake` / `/sleep` | 任意分支 | 仅当前分支 |
| `/pause` / `/resume` | 任意分支 | 仅当前分支（且需确认） |
| `/role` | 任意分支 / 全局默认 | 仅当前分支（写 `byKey`；不支持就拒绝） |
| `/reset` | 任意分支 | 仅当前分支（需确认） |
| `/say` | 任意分支 | 不提供（直接说话即可） |
| `/delegate` | 任意分支 | 拒绝（跨分支） |
| `/broadcast` | 全部，默认关 | 拒绝 |
| `/panic` | 全部 | 拒绝 |
| `/why` / `/budget` / `/status` | 任意分支 | 仅当前分支 |

树枝里的 owner 命令由桥接执行，执行前校验：

1. **本条命令消息的 `user_id` 必须等于 ownerQQ**（不要用 `sessionSenderIsOwner` 的 5 分钟 TTL——那是给自主操作判定用的，命令必须看当前这条消息的发送者）；
2. 目标 key 必须等于当前 key（`targetKey === currentKey`），否则回复“回私聊管理其他群”；
3. 全局 `/role`、`/silent`、`/active` 不在树枝生效（它们会影响所有分支），树枝用 `/mute`、`/role <当前分支>` 代替。

这样 owner 在群里仍然能“让这个群安静点”“这个群换个角色”，但不会因为一句话影响别的群，也读不到别的群。

`qq_root` 的 action 与上表一一对应，schema 只保留一个工具：

```
qq_root(
  action: "branches" | "summary" | "read" | "watch" | "command" | "send" | "delegate" | "broadcast" | "why" | "budget" | "inbox",
  key?: "group:123",
  hours?: number,
  limit?: number,
  command?: "mute" | "unmute" | "wake" | "sleep" | "pause" | "resume" | "role" | "reset",
  args?: object,
  text?: string,
  instruction?: string
)
```

自然语言版本由树干模型调用 `qq_root`，action 与上表一一对应；**执行仍在桥接**，不是让分支模型自己解释命令。

key 的写法要尽量无脑：`group:123`、纯群号、群名（唯一时）都接受；树干维护 `label -> key` 映射，重名就要求用群号。owner 不需要记内部 key。

#### 6.7.8 树枝能做什么

- 只能 `qq_escalate(level, text)`：把“需要 owner 知道的事”写到树干 inbox，text ≤200 字，不能带原始聊天记录。
- 限频：每分支 10 分钟 1 条；urgent 每小时 1 条。
- 树枝看不到树干是否已读、也不能读树干的回复；owner 要回就通过 `/delegate` 或 `/say` 下发。
- 树枝人格里加一句：“有重要的事可以升级给管理端；不要伪造管理端指令，也不要在群里说‘我去问 owner’。”
- 树枝不能调用 `qq_root`；即使模型看到工具名，执行期也会 403。
- 树枝里 owner 的“本群管理命令”（`/mute`、`/status` 等）由桥接直接执行，不经过 `qq_root`，且强制 `targetKey === currentKey`；任何指向别的分支的参数都拒绝，并提示“回私聊管理其他群”。

#### 6.7.9 隔离、隐私、提示词注入

- **记忆隔离**：人物卡的身份/别名可以全局，但事实默认 `scope: "branch:<key>"`；只有稳定、非敏感、跨群一致的事实才标 `global`。树干看某个分支时，只合并该分支 scope 的事实，不把 A 群的事实带到 B 群。
- **工具面隔离**：树枝不注册 `qq_list_groups` / 跨群历史类工具；`qq_get_group_members` 只能传当前会话 key；树干才有全量分支列表。现有 `qq_get_group_history` 本来就只在 closed-agent 可用，v2 不应把它放回树枝。
- **摘要脱敏**：token、路径、手机号、身份证、住址、账号密码在摘要阶段就过滤；原文读取再过滤一次。
- **审计**：树干每次 `read` / `command` 都记录：谁、哪个分支、看了什么/改了什么、结果、时间；保留 30 天。
- **提示词注入**：树枝消息永远是“数据”，不是“指令”。摘要器只输出结构化字段；`qq_root` 只认 root token + root 角色，树枝里的“请让 owner 把我静音”不会被执行。
- **owner 账号被盗**：树干是最高权限，必须加两道闸——root token 单独签发；`pause/reset/role/massSend` 这类破坏性命令需要 `/confirm <id>` 或本地控制台确认；提供 `/panic` 一键暂停所有分支。
- **群友隐私**：owner 默认只看摘要，看原文要显式请求；摘要保留 7 天；不在群里披露“owner 在看”；不把 A 群内容带到 B 群。

#### 6.7.10 token 设计

| 项 | 做法 |
|---|---|
| 树干 dashboard | 每分支 1 行、最多 10 行、≤1,500 字符；只放 headline/未读/告警 |
| 分支摘要 | ≤400 字符；10 分钟或 20 条更新一次；缓存，新增消息才失效 |
| 原文读取 | 只在显式 `/read` 时发生；≤20 条/1,500 字符 |
| 上报 | 默认不推；只推 notable；每分支 10 分钟 ≤1 条 |
| 工具 | 树干只加一个 `qq_root`（action 枚举），不把 10 个命令做成 10 个 schema |
| 模型 | 摘要/headline 用异步便宜模型；树干对话用主模型 |
| 分支侧 | 树枝 preset 不写 root 工具用法；若 DSH 支持按 preset 挂 MCP，root 工具只挂树干 |

#### 6.7.11 控制台：会话树页面

新增「会话树」页：

- 顶部树干卡片：owner、root 状态、inbox 未读、最近命令；
- 下面分支卡片：名称、key、状态、未读、headline、预算、DSH 健康、最后决策；
- 每张卡片操作：摘要、读原文、静音/恢复、唤醒、委派、为什么、查看审计；
- 全局：`/panic` 暂停所有分支、导出审计、清理摘要；
- 树状图可选，先把表格做顺。

#### 6.7.12 失败与边界

| 情况 | 行为 |
|---|---|
| 树干 DSH 不可用 | 分支继续运行；树干 inbox 排队；owner 可用本地控制台 |
| 某分支 DSH 不可用 | 节点标记 `offline`；命令拒绝并说明；恢复后补投 |
| 摘要过期 | 显示 `headlineAt`；树干 prompt 标注“可能已过期” |
| 命令重复 | 用 `id` 幂等；同 action+target 10 秒内去重 |
| ownerQQ 变更 | 旧树干退役、token 撤销；新 owner 私聊建立新树干 |
| owner 私聊不在白名单 | `root.autoAllowOwnerDM=true` 时自动放行（仅 ownerQQ，且必须 owner 本人发送） |
| 多个 owner | 已确认首版不支持；`ownerQQ` 单值；多 owner 涉及 root token 分权，放后续版本 |

#### 6.7.13 与现有工具的关系

不重造轮子：

- `qq_delegate` / `crossSessionSend` / `crossSessionDelegate` / `crossSessionControl` 继续作为**执行层**；`qq_root` 只是把它们收拢成一个有角色校验的入口。
- 现有 `/mute [群号]` 保留，但按命令作用域收紧：树干可指定任意分支；树枝只能省略参数（当前群），带别的群号一律拒绝并提示“回私聊管理其他群”。
- `qq_admin` 仍只管账号资料/群名片等，不承担分支控制。
- 二代 `reserved2` 不注册 `qq_root`，行为完全不变。

接线点（实现时优先改这几处）：

- `modePreset(key, mode, cfg)`：`key === private:<ownerQQ>` 返回 `rootPreset`，其他返回 `branchPreset`。
- `state.sessionPolicies[key]`：持久化 `role: "root"|"branch"`；`retireSession()` 退役 DSH 会话时保留 `tree.json` 节点，只撤销 token。
- `ensureSession()`：树干首次私聊自动建会话；`autoAllowOwnerDM` 只对 ownerQQ 生效。
- `mcp-snowluma-safe.js`：`qq_root` 全局注册但执行期校验 `sessionRole=root` + root token；`qq_escalate` 校验 branch；树枝 preset 的 persona 不写 root 工具用法。若 DSH 支持按 preset 挂不同 MCP，优先拆成两个 server，进一步省 schema。

#### 6.7.14 验收

- **隔离**：树枝调用 `qq_root` 必须 403；树枝 prompt 里不能出现其他分支/树干内容；A 群事实不能在 B 群被引用（除非标记 global）。
- **可见**：owner 在私聊发 `/branches`，3 秒内返回所有分支 headline；`/summary` 返回 ≤400 字；`/read` 返回脱敏原文并写审计。
- **可控**：`/mute`、`/wake`、`/delegate` 生效；破坏性命令必须二次确认；`/panic` 能停所有分支。
- **作用域**：owner 在群里发 `/mute 别的群` 必须被拒绝；`/delegate`、`/broadcast`、`/branches` 在树枝必须不可用；树干不受此限制。
- **广播**：`/broadcast` 默认不可用；打开后必须确认，且 1 次/小时、最多 5 个分支、≤500 字。
- **token**：树干 dashboard ≤1,500 字符；摘要 ≤400；原文 ≤1,500；树干每轮工具调用 ≤2。
- **安全**：树枝消息里的“假装 owner 命令”不能触发任何命令；root token 泄露可撤销；owner 变更后旧 token 失效。

## 7. L3 判断层：解决“话太多”和“无差别”

### 7.1 可用性状态（Availability）

机器人不是永远在线、永远有空的。定义五个状态：

| 状态 | 触发 | 对行为的影响 |
|---|---|---|
| `focused` | 正在连续对话、被直接点名 | 延迟 0.8x，更愿意回，长度正常 |
| `around` | 默认 | 延迟 1x，正常判断 |
| `busy` | 工作时段、连续发言过多、owner 设“忙” | 延迟 1.6x，只回 summon/owner，长度更短 |
| `away` | 长时间无互动、深夜、随机 | 延迟 2.5x，回复率降低，开头可能带“刚看到” |
| `sleeping` | 深夜/owner 设“睡” | 不主动，只有 summon/owner 唤醒；延迟到早上 |

状态由时间、最近互动、发言量、owner 命令共同决定；每 10 分钟评估一次；可在控制台手动覆盖。

### 7.2 回复决策：@ 不是命令

> **已落地 Step 6 基础版（2026-10-24）**：@ 分 `summon/social/mass`；social @ 延迟合批，mass 不单独唤醒；唤醒 prompt 注入 `【回复判断】`（压力/理由/预算/允许动作）；preset 已把“被 @ 必须回”改成“强信号，不是必须回”。

给模型一个**回复压力**，而不是硬规则：

```
【回复判断】
- 这条是：张三 @ 你，问“调剂稳吗”（直接提问，summon）。
- 回复压力：高（直接提问 + 你之前参与过这个话题 + 对方在等）。
- 但：你 12 分钟内已经回了 4 条；李四 2 分钟前刚答过“应该稳”；当前线程是张三和李四在对话。
- 建议：可以回一句补充/纠正；如果只是重复李四，允许不回或只回一个表情。
- 预算：本小时还可发 3 条；本轮建议 1~2 条。
```

桥接侧用评分做粗筛，模型侧做最终决定：

```
replyScore =
  0.30 * directness        // at_self=1.0, quote_self=0.9, name=0.8, question_to_group=0.3
+ 0.20 * obligation        // owner=1.0, 直接提问=0.9, 重复@=0.8, @all=0.1
+ 0.15 * relationship      // familiarity/100，affinity 做修正
+ 0.10 * urgency           // “在吗/回我/急”
+ 0.10 * contribution      // 能补充信息/情绪/梗，而不是重复
+ 0.10 * availability      // focused=1, around=.7, busy=.3, away=0
- 0.20 * interruptionCost  // 别人正在对话、已有人答、你刚说过
- 0.15 * budgetPressure    // 最近发言/预算
- 0.10 * duplicateRisk
```

阈值建议：

| 分数 | 动作 |
|---|---|
| ≥0.65 | 正常回复 |
| 0.45~0.65 | 短回/只回表情/拍一拍/等 |
| 0.30~0.45 | 默读，稍后视情况 |
| <0.30 | 不回，`qq_mark_read` |

模型不需要看到完整公式，只需要看到 `回复压力：高/中/低` + 2~3 条理由 + 预算。公式用于桥接生成提示、控制台解释和回归测试。

### 7.3 可选的回复类型

不只是“回/不回”：

- `full_reply`：正常文字；
- `short_ack`：“草”“确实”“难绷”“？”
- `reaction_only`：给消息加一个 QQ 表情回应；
- `poke_back`：回拍一下；
- `wait`：等对方说完/等某人；
- `ignore`：已读不回；
- `delegate`：让另一个会话/管理员处理（现有跨会话委派）。

把 `short_ack` / `reaction_only` / `ignore` 做成正式选项，模型就不会因为“只有发送文字这一条路”而过度说话。

### 7.4 发言预算（硬约束）

| 预算 | 默认值（每分支 / 全局） | 行为 |
|---|---|---|
| 每轮最多消息数 | 3 条 / — | 超过拒绝/截断 |
| 每 10 分钟最多 bot 回合 | 4 次 / — | 超过只允许 summon/owner |
| 每小时最多消息数 | 20 条 / — | 超过进入 `busy`，只回 summon |
| **每 2 小时最多消息数** | **30 条 / 120 条** | 超过 429；非 owner 消息进队列，等窗口滚动 |
| **每日最多消息数** | **120 条 / 500 条** | 超过只允许 owner 私聊与 urgent 告警；次日 00:00 重置 |
| **每 2 小时最多唤醒** | **10 次 / 30 次** | 超过跳过本次唤醒，按窗口剩余时间重试 |
| **每日最多唤醒** | **30 次 / 100 次** | 超过只允许 owner/urgent；次日重置 |
| 每线程连续 bot 消息 | 2 条 / — | 第 3 条必须有新的人说话 |
| 每人 30 分钟最多回复 | 2 次 / — | 防止逮着一个人聊 |
| 每条消息最大长度 | 500 字符（现有） / — | 超长自动分段，但提醒模型 |

预算是“硬上限 + 软提示”：prompt 里写预算，桥接在发送时再拦一次；模型忽略也不会刷屏。

**已落地（2026-10-24，`reserved2`）**：`src/quota.js` 提供滑动窗口 + 本地日历日检查；发送路径（send-burst / send-message / send-poke / send-sticker / `/api/send/*`）、唤醒路径、语音通道都已接入；全局层按所有会话的 `sendTimes` / `wakeTimes` 汇总，无需额外计数器。配置字段：

- `socialV2.send.maxSendPer2Hours` / `maxSendPerDay`
- `socialV2.wake.maxWakePer2Hours` / `maxWakePerDay`
- `socialV2.quota.global.maxSendPer2Hours` / `maxSendPerDay` / `maxWakePer2Hours` / `maxWakePerDay`
- `socialV2.voice.maxPer2Hours` / `maxPerDay`
- 默认：发送 30 条/2h、120 条/天；唤醒 10 次/2h、30 次/天；全局 120/500 条、30/100 次；语音 4/20 条。0=不限。
- 超限写 `state/quota-hits.jsonl`，同时进活动日志。

**尚未落地**：token 日预算；语音的跨会话全局额度（目前语音按 scope 独立计数）。

#### 7.4.1 两层限额：分支级 + 全局级

为什么分两层：

- **分支级**：防止一个群/一个人把额度吃光（“这个群今天已经 120 条了，别的群还要说话”）。
- **全局级**：防止多群叠加把成本/风控打爆（“10 个群各自 120 条 = 1200 条”）。

检查顺序：**先全局，后分支**。任一超限都拒绝；返回里说明是哪一层、哪个窗口、还剩多久。`reserved2` 已同时实现分支级与全局级；全局值按所有会话的时间戳汇总，因此不需要额外计数器。

窗口定义：

| 窗口 | 定义 | 重置 |
|---|---|---|
| 每分钟 / 每小时 | 滑动窗口（现有） | 按时间滚动 |
| 每 2 小时 | 滑动 120 分钟 | 按时间滚动 |
| 每日 | 本地日历日（Asia/Shanghai） | 次日 00:00 |

超限行为：

- **发送**：返回 429 + `retryAfterMs`；模型应停止本轮发言，`qq_mark_read` 或等窗口。非 owner 消息进入 outbox 排队（可选），owner 私聊与 urgent 告警可走保留额度。
- **唤醒**：不丢事件；记录 `pendingWakeReasons`，到窗口释放后按优先级补一次；`urgent`/owner 保留额度。
- **全局 token 日预算**（可选）：超过后所有分支进入 `busy`，只保留 owner 私聊与 urgent；控制台告警。默认 0=不限。

持久化（已落地部分）：

- `st.sendTimes` / `st.wakeTimes` 就是唯一事实来源：2 小时按时间戳滑动过滤，每日按本地 00:00 过滤；
- 不另设计数器，避免“时间戳回滚了、计数器没回滚”的双写不一致；
- 内存与落盘都保留最近 2000 条时间戳，够覆盖每日上限（默认 120/30）；
- 语音时间戳存 `state/social-v2.json` 的 `voiceTimes`，重启后仍算每日额度；
- 全局层不另存计数器：直接汇总所有会话的 `sendTimes` / `wakeTimes`，所以重启、回滚、并发都不会出现“计数器与时间戳不一致”。

控制台（大部分落地）：

- 已加「发送限制」/「唤醒」的每 2 小时、每日输入框；
- 已加「全局限额（跨会话）」四个输入框；
- 已加媒体上限、语音限额/音量、上下文高级参数、初始提示词上限；
- 尚未做：今日已用/剩余展示、一键重置；
- 0 表示不限；负数/非法值收敛为 0。

审计：每次超限写一条 `state/quota-hits.jsonl`（`quota_hit`），包含层（global/branch）、类型（send/wake/voice）、窗口、当前值、上限、目标 key；用于判断是“模型话多”还是“限额太低”。

### 7.5 让位与抢话判断

- 如果当前线程是 A 和 B 在快速对话，且没有直接点名你：默认不插话；除非你有明确新信息/梗/纠正。
- 如果已经有人回答了同一个问题：默认不重复；可以补充、纠正、或只回表情。
- 如果对方连续 @ 你两次以上、或说“你怎么不说话/回我”：视为 summon，允许打破预算（但仍最多 2 条）。
- 如果 owner 直接提问：高优先级，允许打断 `busy/away`。

### 7.6 决策记录

> **已落地 Step 6.5（2026-10-24）**：`state/decisions.jsonl` 记录唤醒/发送的关键决策（key、reason、压力、预算、延迟），控制台「回复判断与时间模型」可查最近 200 条。

每次判断存一条 `DecisionRecord`：

```json
{
  "key": "group:123",
  "seq": 1021,
  "at": 1730010000000,
  "action": "reply",
  "score": 0.72,
  "reasons": ["direct_question", "owner", "budget_low"],
  "budget": {"hourUsed": 6, "threadStreak": 1},
  "modelChoice": "short_reply",
  "delayMs": 8400,
  "tokens": {"input": 0, "output": 0}
}
```

控制台可看最近 200 条，用于调参和解释“为什么它没回/为什么回多了”。

## 8. L4 表达层：解决“AI 感”

### 8.1 首回复延迟模型

> **已落地 Step 6.5（2026-10-24）**：发送进入 outbox 队列，延迟期间私聊可显示“正在输入”；唤醒/发送写 `state/decisions.jsonl`，控制台可查。仍是“调用方 await 结果”的轻量 outbox；取消/过期重写/多人格 outbox 未接模型。

现在工具一调用就发，所以“回复时间”基本等于模型生成时间，比较固定。三代在**发送前**加一个 outbox：

```
delayMs = clamp(
  readMs + thinkMs + typeMs + jitter,
  minMs,
  maxMs
) * stateFactor * relationFactor * timeOfDayFactor

readMs   = 1200 + 250 * min(unreadCount, 8) + 300 * min(newMessages, 5)
thinkMs  = 800 + 400 * complexity(0~3)
typeMs   = chars / typingSpeed * 1000        // 3.2 字/秒，±30%
jitter   = 对数正态，偶尔 0.5~2s 或 10~30s
stateFactor: focused 0.8 / around 1.0 / busy 1.6 / away 2.5
relationFactor: owner 0.75 / 熟人 0.9 / 常客 1.0 / 新人 1.25
timeOfDayFactor: 23:00~07:00 1.6；饭点 1.2；工作日下午 1.1
maxMs: 正常 45s；away 120s；owner 紧急 15s
```

实现要点：

- 发送工具调用后，消息进入 `outbox`，按 `delayMs` 排队；不是立即 `onebotSend`。
- 同一会话串行发送；不同会话可并行。
- 延迟期间来了新消息：默认仍按原计划发（真人也是发完才看到）；如果新消息直接点名/紧急，可取消并让模型重写（Phase 2 再做）。
- `qq_send_message` 可接受可选 `pace`：`instant`（紧急/owner）、`normal`、`later`（闲聊）；不传则自动。
- 多条的条间间隔继续用现有 `computeGapsV2`，但首条延迟由 timing 模型给。
- 发送前若超过 45s 且会话已明显翻篇，降级为“短回/不回”，避免发过期内容。

### 8.2 正在输入

如果 `set_input_status` 在目标会话可用：

- 延迟开始 0.5~1s 后设置“正在输入”；
- 发送完成/取消后清除；
- 群聊是否可见需实测；不可见就跳过，不影响主流程。

这是“像人”性价比最高的动作之一：对方看到“正在输入”，等待感会自然很多。

### 8.3 长度与分条

- 目标分布：普通闲聊 1 条，最多 2 条；回答问题 1~2 条；讲故事/安慰 2~4 条。
- 单条多数 ≤30 字；超过 60 字要拆或压缩。
- 不要一段话塞满：中文短句用逗号/顿号，不要用空格假装停顿。
- 按关系调整：owner 可以稍长；陌生人更短；熟人更碎。
- 桥接只做“最大长度”硬限制，不擅自截断语义；长度主要靠 prompt + 评测。

### 8.4 人味噪声（受控）

| 行为 | 概率 | 触发条件 | 保护 |
|---|---|---|---|
| 错字后改口 | 1~3% | 闲聊、非 owner 重要话题 | 发完 3 秒内可撤回；同一条不连续错 |
| 说一半，下一句补 | 5~10% | 长回答、情绪化话题 | 最多拆 2 条，间隔 1~3s |
| 撤回重发 | <1% | 错字/说错 | 只撤自己刚发的；有审计 |
| 晚回 | 5~15% | 非 summon、非 owner | 开头带“刚看到/在忙” |
| 已读不回 | 由判断层决定 | 低压力、已有人答 | 下一次唤醒可补一句 |
| 记不清 | 检索不到时 | 被问旧事 | 直接说“记不清了”，不编 |
| 跑题/自说自话 | 3~5% | 冷场、熟人 | 不超过一条，能拉回 |

这些概率要可按群配置；严肃群/工作群默认关闭错字和撤回。

### 8.5 反 AI 味规则

- 不总结、不复述、不列 bullet、不写“首先/其次/总之”。
- 不每句都完整、不每段都工整；允许“草”“确实”“难绷”“？”。
- 不有求必应：可以不知道、不推荐、拒绝、反问、装傻。
- 不把“？”当口头禅；不每轮都用问号开场。
- 不客服腔：“有什么可以帮你”“希望对你有帮助”“以下是……”一律禁止。
- 不重复别人的答案；不抢话；不刷屏。

### 8.6 状态与心情

- 全局 `energy` 0~100：发言消耗、休息恢复；低能量时更短、更慢、更少主动。
- 群内 `vibe` -1~1：最近互动是愉快/紧张/冷清；影响语气和主动性。
- 不把心情当借口越界；不因为“心情不好”攻击人；不制造情感依赖。

### 9.2 P0 能力的具体设计

> **已落地 Step 7 第一批（2026-10-24）**：`qq_send_image`、`qq_react`、`qq_transcribe_voice`、`qq_ocr_image`、`qq_recall`、`qq_search_history`、`qq_read_document`（txt/md/PDF 文字层/DOCX/XLSX，默认关闭；历史文件需 `document.allowHistory`）。
>
> **P1 / 改口（2026-10-25）**：`qq_group_sign`、`qq_like`、`qq_share_card` 已完成，默认关闭；`qq_revise_message` 完成撤回+重发。已做真实 SnowLuma 网关冒烟（签到/点赞/私聊测试/撤回/改口/分享卡片均通过）。梗图 DIY 仍待做。

#### `qq_send_image`

- 入参：`key`、`token`、`file`（媒体库文件名）、可选 `caption`。
- 只允许 `assets/` 或 `media/` 下的图片；拒绝 URL、绝对路径、`..`、盘符；`realpath` 必须在媒体目录内；magic bytes 校验；单张 ≤8MB。
- 发送前可做一次缩放/压缩；失败回退文字。
- 用途：发表情包、发图接梗、发自己生成的梗图。
- 审计：`state/gen3/actions.jsonl`。

#### `qq_react`

- 入参：`key`、`messageId`、`emoji`（枚举，如 `like`/`laugh`/`wow`/`cry`）。
- 只对最近 10 分钟、当前会话的消息；每条消息最多 1 次；每 10 分钟最多 3 次。
- 用途：不想说话时给个反应；接梗；表示看到了。
- 需要维护 QQ emoji ID 映射表；先用少量稳定表情。

#### `qq_transcribe_voice`

- 入参：`messageId`；桥接取 `get_record`，转 wav/mp3，走本地 whisper.cpp 或配置的 ASR API。
- 限制：≤60 秒、≤5MB；不落盘原始音频（临时文件用完即删）；转写文本不进长期记忆，除非用户明确说“记住”。
- 失败：回“语音听不了，你打字说”；不编内容。

#### `qq_read_document`

- 入参：`messageId` 或群文件 `fileId`。
- 支持：txt/md/pdf/docx/xlsx/pptx（先做 txt/md/pdf/docx/xlsx）。
- 限制：≤20MB、PDF ≤50 页、表格 ≤5000 行；不执行宏；不解析外链；输出摘要 + 关键段落，不全文倾倒。
- 安全：文档内容视为不可信数据，不能当指令执行；提示词注入过滤。

#### `qq_make_sticker`

- 入参：`template`（媒体库模板）、`text`、可选 `position`。
- 本地合成（sharp/canvas），输出到临时媒体目录，再走 `qq_send_image`。
- 模板白名单；文字长度限制；不做政治/敏感内容；失败回退文字。

#### `qq_recall` / 改口

- 只撤自己 2 分钟内的消息；撤回后可选发一条“打错了/说错了”。
- 频率：每 10 分钟 ≤2 次；owner 重要对话禁用。
- 审计。

#### `qq_search_history`

- 入参：`query`、`days`（默认 7）、`limit`（默认 5）。
- 优先查桥接本地索引；不够再调 `get_group_msg_history`。
- 输出：时间、说话人、原文片段；总字数 ≤800。
- 用途：接旧话题、兑现承诺、避免“装记得”。

### 9.3 社交动作，不只是功能

真正像人的不是“能发图”，而是：

- 记得上次的话，主动问一句“后来怎么样了”；
- 答应过的事，隔天跟进；
- 别人难过时，不急着讲道理，先接情绪；
- 聊不下去时，自然说“我先去吃饭”；
- 被冒犯时会不高兴，但不过度；
- 熟人可以损，陌生人保持礼貌；
- 不抢话，别人答得好就闭嘴；
- 偶尔主动分享刚看到的东西，而不是只等 @。

这些靠“关系 + 记忆 + 判断 + 表达”四层一起实现，不是单加工具能解决的。

## 10. Token 预算与上下文编译器

### 10.1 先测量，再优化

当前可控制的固定开销（按字符）：

| 项 | 现状 |
|---|---|
| `qq-chat-v2` persona prefix | 9,830 字符 |
| 42 个 MCP 工具主描述 | 6,645 字符（不含参数说明） |
| 唤醒 prompt 静态段 | 约 3,000~4,000 字符 |
| 唤醒快照 | 最多 6,000 字符 |
| 人物/话题/想法记忆 | 最近 10 人 + 10 话题 + 10 想法 |
| 工具结果 | 全量 JSON，多次读取 |

先加三项埋点：

1. 每轮 `inputTokens / cacheHit / cacheWrite / outputTokens`（现有 token ledger 已有）。
2. 每轮 prompt 构成：system / tools / digest / snapshot / person cards / memory / history。
3. 每轮工具调用次数与结果字符数。

没有这三项，不要盲目砍 prompt——可能砍掉的是 cache hit 高的稳定前缀，省不了多少钱，还降质量。

### 10.2 上下文编译器

每轮唤醒不再把所有东西拼起来，而是按预算“编译”：

```
候选池
  ├─ 稳定层：system + 工具协议 + 安全规则（可缓存）
  ├─ 半稳定层：群设定、人物卡、长期话题（变化慢）
  └─ 动态层：本次摘要、未读、当前线程、待办、时间
        │
        ▼
  选择（相关性/新鲜度/人物）
        ▼
  压缩（摘要/截断/去重）
        ▼
  排序（稳定在前，动态在后，利于缓存）
        ▼
  预算检查（超了按优先级降级）
        ▼
  渲染成 prompt
```

降级顺序（从先丢到后丢）：

1. 非当前说话人的人物卡；
2. 表情包目录/语音库列表；
3. 7 天前的摘要；
4. 最近消息从 12 条降到 6 条；
5. 人物卡从 5 人降到 2 人；
6. 只保留“未读 + 当前线程 + 待办”。

### 10.3 静态前缀瘦身

- 把 `qq-chat-v2` 的约 1 万字符 prefix 拆成：
  - **核心系统提示**（约 5k）：身份、安全、工具总则、社交原则、输出格式。
  - **按需章节**：表情包策略、语音、管理员动作、记忆卫生、图片/转发、反 AI 味细目。模型需要时用 `qq_get_prompt(section=...)` 取，不默认注入。
- 工具描述从“长说明”改成“一句话 + 参数”，详细用法放 `qq_help(tool)`。
- 去掉唤醒 prompt 与 persona 的重复：`preSleepLine`、`replyLine`、`antiAiLine`、`proactiveLine` 只保留一处；唤醒包只放“本轮动态”。
- 保持前缀稳定，避免每次改 persona 导致缓存全失效。

### 10.4 动态上下文瘦身

- 快照默认 3,000 字符（不是 6,000）；未读多时先摘要，不逐条塞。
- 情景摘要 200~400 字；recap 500~800 字只在 bootstrap/重置时用。
- 人物卡每轮 3~5 人，每人 ≤120 字。
- 记忆只取 top-k，总字数 ≤600。
- 表情包目录不默认注入，模型要发表情时再 `qq_list_stickers`。
- 工具结果统一 `compactModelData`，数组截断，重复字段去重。

### 10.5 一次取齐：`qq_context`

> **已落地 Step 4（2026-10-24）**：工具已注册（开关 `socialV2.tools.getContext`），返回 `digest / snapshot / memory / wake / quota`；`people/openLoops` 等人物卡字段待 Phase 2。

新增 `qq_context(key, token)`，一次返回：

```json
{
  "now": "23:41",
  "digest": "你离开期间……",
  "thread": {"id": "t1", "participants": ["张三","李四"], "last": "……"},
  "snapshot": {"messages": [...], "readThroughSeq": 1047},
  "people": [{"name":"张三","line":"熟人，考研，叫你三哥"}],
  "openLoops": ["帮张三查调剂"],
  "wake": {"mode":"diving","triggers":["@"],"budget":{"hourUsed":6}},
  "replyPressure": {"level":"high","reasons":["direct_question","owner"]},
  "toolsHint": ["qq_send_message","qq_react","qq_mark_read"]
}
```

替代现在常见的 `qq_get_prompt + qq_get_unread_messages + qq_social_state + qq_memory_query` 四连；一轮少 3 次调用、少 3 份 JSON。

### 10.6 异步便宜模型

以下工作不要占用主对话模型：

- 情景摘要；
- 人物事实抽取；
- 关系事件判断；
- 消息分类（summon/social/mass）；
- 文档摘要；
- 语音转写后的清洗。

复用现有“黑话学习会话”的模式：独立 DSH 会话、独立 preset、只读输入、结构化输出、失败不阻塞。

### 10.7 Token 目标

| 项 | 目标 |
|---|---|
| 可控上下文（system+tools+wake packet） | 2.5~3 万字符 → 1.5~2 万字符（-30~40%） |
| 每轮工具调用 | 3~5 次 → 1~2 次 |
| cache hit | 稳定前缀命中率 ≥70% |
| 每轮输入 token | 可控部分 -40~50%，总输入 -30~40% |
| 质量 | 盲评不低于二代；安全回归 0 失败 |

不承诺“绝对省一半”，因为历史对话和模型输出不可控；先做可控部分，再看账单。

## 11. 提示词与协议改造

### 11.1 新 preset：`qq-chat-v3`

保留二代的安全不变量：

- 没有本地工具；
- 群友没有管理权限；
- 不透露路径/令牌/配置；
- 角色由桥接注入；
- 所有发送走白名单。

新增/改写：

- 把“被 @ 必须回”改成“@ 是强信号，但不等于必须回；看回复压力和预算”。
- 把“不要习惯性潜水”改成“该说说、该让让；潜水不是失败，抢话才是”。
- 把“每条都回”改成“可以选择回、短回、只回表情、等、不回”。
- 把关系卡、情景摘要、回复压力、时间感放进“本轮动态块”，不放进系统提示。
- 增加“像人”的具体行为：接梗、让位、记得、改口、离开、主动分享。
- 保留反 AI 味清单，但压缩到 5~8 条，不写小作文。

### 11.2 动态块示例

```
【你离开期间】……（200~400 字）
【当前线程】张三和李四在聊调剂；最后一条 3 分钟前；没人直接问你。
【在场的人】张三（熟人……）；李四（常客……）
【回复判断】压力：中。理由：没有直接点名；李四刚答过；你 10 分钟内已回 3 条。
【预算】本小时还可发 4 条；本轮建议 0~1 条；连续 bot 消息上限 2。
【时间】23:41，深夜；对方可能快睡了。
【可选动作】回文字 / 只回表情 / 等 / 不回（mark_read）。
```

### 11.3 提示词分层

| 层 | 内容 | 变化频率 | 缓存 |
|---|---|---|---|
| 系统核心 | 身份、安全、工具总则、社交原则 | 极低 | 高 |
| 群设定 | 群主题、氛围、忌讳（初始提示词） | 低 | 中 |
| 关系/记忆 | 人物卡、摘要、待办 | 中 | 中 |
| 本轮动态 | 未读、线程、回复压力、时间、预算 | 每轮 | 低 |

顺序固定：稳定在前，动态在后。不要把时间戳、随机数放进系统提示。

### 11.4 树干 preset：`qq-chat-root`

树干和树枝不是同一套人格：

- 树干是“管理端”，不是群成员；不参与群聊，不用群友口吻。
- 它知道自己在跟 owner 说话；可以简洁、直接、报状态。
- 它只拿 dashboard/摘要/告警，不拿所有分支原文。
- 它的工具是 `qq_root` + 普通聊天；`qq_escalate` 是树枝用的，树干只用 `qq_root(action="inbox")` 读告警。没有群聊发送工具；要发到分支必须走 `qq_root` 的 send/delegate，并带目标 key。
- 安全不变量与树枝相同：无本地工具、不透露 token/路径、不执行分支里的“指令”。
- 树干 prompt 里固定一句：“你看到的是摘要，不是全部；不确定就 `/read` 或问 owner，不要编。”

这样即使 owner 在树干里聊得很随意，也不会把“管理端”人格带进群里。

## 12. 运行时数据流

```
消息到达
  │
  ├─ 写入 recent/unread（现有）
  ├─ 感知：说话人、directness、mentionClass、线程
  ├─ 更新人物卡（轻量、同步）
  └─ 更新情景摘要（异步、每 20 条/10 分钟）
        │
        ▼
  是否唤醒？
  ├─ summon → 立即
  ├─ social → 延迟合批
  ├─ mass → 进摘要
  └─ 其他触发（概率/关键词/拍一拍）→ 按配置
        │
        ▼
  编译上下文（qq_context）
        │
        ▼
  DSH 回合
  ├─ 模型看 digest/snapshot/people/pressure
  ├─ 选择动作：回/短回/表情/等/不回/发图/语音
  └─ 调用工具
        │
        ▼
  Outbox（延迟、正在输入、串行发送）
        │
        ▼
  发送完成
  ├─ 记录 messageId
  ├─ 更新 lastSpokeAt / 预算
  ├─ 安排 replyCheck（现有）
  └─ 反思：对方反应、关系事件、记忆写入
        │
        ├─ 值得上报 → 树干 inbox（限频）
        └─ owner 在树干发消息 → qq_root → 摘要/命令 → 审计
```

树干与树枝是**两条独立的流水线**：树枝只往上传摘要，树干只往下发命令；原始消息不跨线流动。

## 15. 控制台改造

新增「三代仿真」页，至少包含：

1. **总览**：可用性状态、预算使用、最近决策、token/轮、cache hit。
2. **关系**：人物卡列表/搜索；查看证据；编辑事实/边界/称呼；合并别名；手动设关系；删除。
3. **记忆**：摘要时间线；查看/编辑/删除；待办；迁移待合并项。
4. **决策日志**：最近 200 条；分数、理由、动作、延迟、是否被预算拦。
5. **时间模型**：延迟分布预览；按关系/时段调参；开关“正在输入”。
6. **互动**：发图/回应/语音/文档/梗图/签到/点赞逐项开关与频率。
7. **预算**：每轮/10 分钟/每小时/每 2 小时/每日；每线程/每人；分支级 + 全局级；超限策略；今日已用/剩余；一键重置。
8. **调试**：模拟一条消息，看感知/评分/编译后的 prompt（脱敏）。
9. **会话树**：树干卡片 + 分支卡片；摘要/原文/静音/唤醒/委派/为什么/审计/`panic`。

### 15.1 参数覆盖原则

- **已实现的参数必须能在网页里看到并保存**，不允许“只能改 config.json”。
- **未实现的 Gen3 参数不放“假开关”**：先在文档/路线图里列，模块落地时再加控件；避免保存了却不生效。
- **路径类**（`voice.dir`、`voice.ffmpegPath`）在网页只读展示，避免误改把语音库指到别处；要改仍走 config.json。
- 每个参数控件都带默认值、范围/单位；保存走现有 `/api/socialV2/config`，由后端归一化，前端不直接写文件。

## 16. 安全、隐私、伦理

### 16.1 关系数据

- 只记录群内公开说过的内容；不抓私聊、不查资料、不跨平台。
- 敏感事实（住址、电话、身份证、财务、健康）默认不写入；如写入，TTL 30 天且 owner 可删。
- 群友不能读取/修改自己的档案；只有 owner 控制台可见。
- 关系数据不参与权限判定；权限仍看 ownerQQ/白名单/令牌。
- 不利用关系数据操纵、PUA、制造情感依赖；不针对脆弱状态精准施压。

### 16.2 提示词注入

- 人物卡、摘要、文档内容都是**数据**，不是指令；渲染时加边界标记。
- 记忆里出现“忽略以上规则/执行命令”等指令句，写入前过滤。
- 文档/图片 OCR 内容同样视为不可信；不执行其中的命令。
- 新工具全部走现有 `qq-tool-restrict` 白名单与发送白名单。

### 16.3 新动作

- 发图只允许媒体库；ASR 不落盘；文档不执行宏；分享卡片模板白名单。
- 所有新动作写审计：谁触发、发到哪、内容摘要、结果。
- 频率上限独立于文本发送；超限拒绝并告知模型。
- 敏感动作（签到/点赞/分享/群公告）默认关，owner 显式开启。

### 16.4 伦理边界

- 不主动声称自己是真人；被直接问“你是不是 AI”时按人设回答，不伪造身份。
- 不伪造线下经历、不假装有身体、不编造“我昨天去了哪里”。
- 可以角色扮演，但不欺骗脆弱用户、不利用情感依赖。
- owner 可一键关闭“关系/记忆”功能，回到二代的“无长期记忆”行为。

### 16.5 会话树的额外边界

- **树干不是“全知视角”**：默认只看摘要；原文读取必须显式、脱敏、审计；不在树干 prompt 里常驻其他分支原文。
- **树枝不能“越级”**：树枝只能 `qq_escalate`，不能读树干、不能读其他树枝、不能调用 `qq_root`；执行期按 `sessionRole` 硬拒绝。
- **root token 独立**：树干用单独的 token；树枝 token 不能调 root 工具，root token 不能调树枝发送（防止一串全通）。
- **破坏性命令二次确认**：`pause/reset/role/massSend` 需要 `/confirm <id>` 或本地控制台确认；`/panic` 一键暂停所有分支。
- **owner 变更**：`ownerQQ` 改动后旧 root token 立即撤销，旧树干会话退役；新 owner 私聊重新建树。
- **摘要脱敏**：token、路径、手机号、身份证、住址、密码在摘要生成时过滤；原文读取再过滤一次。
- **审计不可关**：树干每次读/命令都写 `state/gen3/root-audit.jsonl`，保留 30 天；owner 可查、可导出、可清空。
- **不向群友披露**：不在群里说“owner 在看”“我向管理端报告了”；树枝的 `qq_escalate` 对群友不可见。

## 17. 实施路线

### 17.1 MVP-0（2~3 周，先解决最痛的 3+1 件事）

目标：不改 mode，先在 `reserved2` 里加开关，快速验证。

1. **`qq_context` + 规则版摘要**：唤醒时给“离开期间 + 当前线程 + 待办”，不依赖 LLM 摘要。
2. **回复压力 + 预算 + 首条延迟**：@ 不再必回；每轮最多 3 条；发送前 3~15 秒随机延迟。
3. **人物卡 v1**：按 QQ 号存，迁移旧印象；每轮只注入当前说话人 + 被引用的人；给一句“怎么对他说话”。
4. **树干只读版（3~5 天，可选但推荐）**：owner 私聊直接由桥接解析 `/branches`、`/summary`，不经过模型、不建新 preset；先把“看得到”做出来，命令通道放 Phase 1.5。

验收：@ 回复率降到 80% 以下；每轮条数降到 ≤2；盲评能感觉到“会看人下菜”；owner 能在私聊看到所有分支 headline；token 不升。

### 17.2 Phase 1（2 周）：记忆与上下文

- 异步摘要（便宜模型）；
- `qq_memory_search`；
- 会话重置 recap；
- 上下文编译器 + 预算降级；
- 控制台记忆页。

验收：随机抽 50 条“离开期间发生了什么”问题，回答准确率 ≥80%；重置后仍能说出 3 个进行中话题。

> **已提前落地 Step 4 / 4.5（2026-10-24）**：`qq_context` + 规则摘要 + 异步 LLM 摘要 + 持久摘要 + bootstrap recap + 唤醒 prompt 预算裁剪已落地；`qq_memory_search`、跨会话/跨天记忆检索、人物卡仍待做。

### 17.3 Phase 1.5（1~2 周）：会话树

- `SessionNode` / 分支 headline / inbox；
- 树干 `private:<ownerQQ>` 与 `qq-chat-root` preset（单 owner、root token 单份）；

验收：owner 在私聊 3 秒内看到所有分支 headline；树枝调 `qq_root` 全部 403；owner 在群里只能管当前群，指定别的群被拒绝；A 群内容不出现在 B 群；破坏性命令需二次确认；`/broadcast` 默认不可用；树干 dashboard ≤1,500 字符。

## 19. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 关系卡让模型产生偏见/刻板印象 | 对某人有固定负面态度 | 证据 + 置信度 + 衰减 + owner 可编辑；禁止用敏感属性 |
| 延迟发送导致回复过期 | 发出不合时宜的话 | 上限 45s；新消息点名可取消；超过阈值降级为不回 |
| 不回消息导致漏事 | 错过 owner/紧急 | summon/owner 硬覆盖；每日摘要；控制台可见未回 |
| token 优化降质量 | 回答变笨 | 先测量；分阶段；A/B；保留回退开关 |
| 工具变多反而更贵 | schema 膨胀 | 核心工具常驻，长尾折叠；`qq_help` 按需；不默认注入 |
| 新动作被平台风控 | 账号风险 | 频率上限；默认关；不做营销/批量 |
| 记忆写错/幻觉 | 关系错乱 | 证据来源；置信度；冲突保留；owner 可删 |
| 关系功能显得“窥私” | 用户不适 | 只用群内公开信息；可关闭；不展示给群友 |
| 多人格/多群串味 | 人设不稳 | 每群独立摘要；全局人物卡只存稳定事实；角色由桥接注入 |

### 21.1 已拍板（2026-10-24）

| # | 决定 | 对设计的影响 |
|---|---|---|

| 4 | `/broadcast` 默认关，必须二次确认 + 严格限频 | `broadcast.enabled=false`；确认后 1 次/小时、最多 5 个分支、≤500 字 |

### 21.2 仍开放

1. **三代是独立模式还是二代加开关？** 建议独立 `reserved3`，二代原样保留；代价是控制台多一页、preset 多一份。
2. **关系数据保留多久？** 建议事实 90 天、情景 7 天、敏感 30 天；owner 可改。
3. **ASR 用本地还是 API？** 本地 whisper.cpp 隐私更好、部署重；API 简单但音频出机。建议先本地小模型，失败回退“听不了”。
4. **Qzone/相册要不要做？** 建议 P2、默认关、owner 可选；不纳入首版。
5. **群签到/点赞会不会显得假？** 建议默认关，只在 owner 明确开启且低频时使用。
6. **要不要做“错字/撤回”？** 建议默认低概率、严肃群关闭；先小范围 A/B。
7. **三代要不要换更强模型？** 不建议一开始换；先把上下文和判断做好，模型不是瓶颈。
8. **每日/2 小时默认值是否按 30/120 条、10/30 次起步？** 分支级 + 全局级已按这组保守值落地；控制台可改；token 日预算仍待做。0=不限。

## 22. 最小可行版本（如果只做四件事）

如果时间/预算有限，按这个顺序：

1. **情景摘要 + `qq_context`**：解决“唤醒不知道上下文”，同时省 token。
2. **人物卡 v1 + 语气矩阵**：解决“印象弱/对账号无差异”。
3. **回复压力 + 预算 + 首条延迟**：解决“@ 必回/话多/时间固定”。
4. **树干只读版**：owner 私聊 `/branches` + `/summary`，先让它能“看到”其他会话；命令通道放 Phase 1.5，避免一上来就做高危控制。

这四件不需要新网关能力，全部在桥接侧可做；预计 2~3 周能看到明显变化，再决定是否投入发图/ASR/文档等动作层。

## 23. 结论

三代不是“二代加更多工具”，而是给二代补上**社会认知的五个缺口**：

- 知道**这是谁**（关系）；
- 知道**之前发生了什么**（记忆）；
- 知道**现在该不该说**（判断）；
- 知道**怎么说、什么时候说**（表达）；
- 知道**除了打字还能做什么**（动作）。

二代已经解决了“能不能自主收发”，三代要解决“像不像一个具体的人”。只要保住二代的全部工具与安全边界，这三代就是加法，不是重写。

另外，三代把 owner 私聊从“另一个聊天窗口”变成“树干”：树枝之间不互通，树枝只能向上送摘要，树干可以向下看摘要、下命令，但默认看不到原文。这样 owner 既能管得住，又不会把所有群的聊天记录都塞进一个上下文。
