架构

qq-bridge 由哪些进程组成、一条 QQ 消息怎么走到模型、回复怎么回到 QQ。as of 2026-11-03，对照上游 dev b80fa51 的代码。行内出处写作 文件 · 函数，未标文件的函数都在 src/bridge.js。

进程
3 个

SnowLuma、qq-bridge、DSH Web 各自独立运行；桥接不启动、不控制另外两个。

端口
3000 · 3001 · 3080 · 3100

OneBot HTTP · OneBot WS · DSH Web · 本地控制台。

模式
4 种

chat · closed-agent · reserved · reserved2，真值存在 DSH 的 qq-mode 设置里。

MCP server
3 个

由 DSH 按 profile 的 cordis.patch.yml spawn，代码在本仓库 src/。

一条消息怎么进来

SnowLuma 的 WS 事件由 main 里注册的回调接住：私聊、群聊交给 handleIncoming，拍一拍交给 handlePokeNotice，撤回交给 handleRecallNotice；机器人自己发的消息在回调里先被丢掉。handleIncoming 依次做：

步骤做什么出处
准入会话 key（group:群号 / private:QQ号）先过白名单与当前模式，再过忽略名单modeAllowed · allowed · isSessionAllowedInCurrentMode
解析消息段转成两份文本：带引用信息的给模型，只含本条文字的用来判命令；同时抽出图片等媒体segmentsToText · extractMediaFromSegments
挂起回答该会话有 agent 的提问或审批在等时，管理员这条消息当作回答；群友消息不会被吞handlePendingAnswer
管理命令以 / 开头且发送者是 ownerQQ 时由桥接直接执行（如 /role），不经过模型；其余 / 内容原样交给 DSHhandleIncoming 内联
分流按模式走三条路之一，见下表
chat · closed-agent

拼上角色提示，进按会话 FIFO 的投递队列，deliverPrompt 调 sessions.prompt。模型回合结束时的文字由桥接自动发回 QQ。closed-agent 只放行管理员私聊。

reserved（一代仿真）

同样走投递队列，但先过一个观望 / 活跃 / 试探 / 退场的状态机决定何时投递、投递什么；回合文字同样自动发回。isSocialEnabled · scheduleSocialReply

reserved2（二代仿真）

消息只记进本地会话流水，由唤醒调度决定何时叫醒模型。模型的文字输出不会自动发送，要说话必须调 MCP 工具。appendSocialV2Message · scheduleWakeV2 · sendWakePromptV2

和 DSH 怎么对接

会话

每个 QQ 会话对应一个 DSH 会话，映射存在 state/sessions.json。建会话时挂到同一个 workspace，必须带上当前模式的 preset，并预分配一个把 QQ 会话 key 编码进去的 sessionId。ensureSession · modePreset

事件

主进程常驻读 events.mux：turn/start 建回合收集器，回合结束时取文本；question/requested、approval/requested 转成发给管理员的 QQ 消息并登记挂起。pumpMux · registerPending

设置

每 5 秒调一次 settings.describe：读 qq-mode 命名空间得到当前模式和 ownerQQ，读 agent-presets 的默认 preset；连不上就重新发现 DSH 端口。模式变化时清理旧模式的定时器和排队投递。startDshWatch · checkDsh · refreshMode

preset

chat、reserved 用 agentPreset（默认 qq-chat），reserved2 用 socialV2.agentPreset（默认 qq-chat-v2），两者都是 strict：preset 不在 DSH 清单里就拒绝建会话。closed-agent 用 qq-mode 里的 closedAgentPreset，空则用 DSH 默认 preset。modePreset · resolvePresetName

回复怎么出去

发往 QQ 的路有两条，最后都落到 SnowLuma：

自动回复工具发送
用在chat、closed-agent、reserved：模型回合结束时的文字reserved2 的 qq_send_message 等工具，以及控制台手动发送
路径pumpMux → auditAndSend → sendToQQ → SDK sendGroupMessage / sendPrivateMessage（WS）MCP snowluma → 桥接 /api/send/*、/api/socialV2/send-* → onebotSend → OneBot HTTP send_group_msg / send_private_msg
出站检查SENSITIVE_RE（src/sensitive.js）与已知会话令牌片段，命中则拦下并按 security.interceptNotify 发一条拦截提示端点侧做同口径检查；onebotSend 自己再拦一次含会话令牌的文本
整形Markdown 转纯文本、按长度分段、逐段间隔 sendDelayMs由工具参数决定分条（messages 数组）与引用、@

几个结构上的取舍

发送只经桥接

MCP 的发送工具不直连 OneBot，而是调桥接的 HTTP API，出站审计只在桥接实现一份。src/mcp-snowluma-safe.js 文件头

身份来自 sessionId，不来自参数

MCP 协议里没有「调用来自哪个会话」。守卫从 exec.agent.id（桥接预分配的 sessionId）解出会话 key，与工具参数里的 key 比对，不一致就拒绝。plugins/qq-agent-presets/qq-self-key.mjs · qq-tool-restrict.mjs

群聊会话 fail-closed

非 closed-agent 的会话拿不到 qq-chat* preset 就不建，宁可不回也不让 DSH 默认 preset 把本地工具暴露给群。resolvePresetName

控制台只在本机

只监听 127.0.0.1，必须带 consoleToken（未配置时自动生成存进 state/console-token）；MCP 调用另带每会话的 x-agent-token。startConsoleServer

启动顺序

main 依次：读 config.json、建 state/ 并收紧 ACL、拿单实例锁、读会话状态；加载黑话库与表情库；建 DSH 客户端；建 SnowLuma WS 客户端并注册事件回调；bot.connect()（失败不阻塞，SDK 后台重连，断线或报错时尝试重新发现 token）；预热表情库；启动 DSH 轮询、SnowLuma 健康轮询、控制台；最后进入 pumpMux 常驻读事件。main · healTokenIfStale

代码注释与实现不一致的两处
  • src/mcp-snowluma-safe.js 的会话绑定注释说「桥接为每个 QQ 会话派生一个 MCP 进程，spawn 时注入 QQ_BRIDGE_SELF_KEY」。仓库里没有任何地方设置这个环境变量；MCP 由 DSH 按 profile 启动，实际生效的会话绑定在 preset 守卫一侧（见上文「身份来自 sessionId」）。
  • 同一文件头写「所有调用走 OneBot HTTP API」，但发送类工具实际调的是桥接的 /api/*（文件后文也这么写）；直连 OneBot HTTP 的只有只读工具。
