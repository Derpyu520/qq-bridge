用量账本

三、数据从哪来（三个来源，各管一段）

DSH 会话日志
  ├─ assistant/message.data.usage ──► 逐轮明细（每条一次采样）
  ├─ llm/retry-started ─────────────► 重试轴（同一步骤的第二次请求另算一次）
  └─ session/follow 开场快照
        ├─ projections.tokenUsage ──► 累计总量（整条日志的权威值）
        └─ records[]（最多 200 条） ─► 历史逐轮回填
维度来源精度
累计总量（每会话 / 全局）DSH 的 tokenUsage 投影，经 session/follow 开场快照下发精确，且包含桥接启动之前的历史
逐轮明细assistant/message 的 usage 折叠精确；但只覆盖「桥接运行期间 + 开场快照窗口内」的回合
金额读取时用价目表折算按每条采样自己的时间点判定高峰/空闲

三条实现要点：

  1. 不自己累加总量。 桥接重启、换会话、会话退役都不会让总量失真——总量永远等于 DSH 报的投影值加上「基线之后」的增量。
  2. 幂等折叠。 重连时 DSH 会重新下发开场快照。账本按 (session, turn, step, retry) 建键，且只有 seq 严格更新才覆盖，所以重放不会让用量翻倍。
  3. 先落盘再进内存。 pumpMux 的 finally 会在断线时清空所有 per-turn 状态（否则重连后回复会重复累加），所以每条采样一到就 append 到 state/token-usage.jsonl，内存只是它的投影。

四、计价口径

官方价目表（元 / 百万 token），高峰时段单价 = 空闲时段的 2 倍：

模型缓存命中（空闲）缓存未命中（空闲）输出（空闲）
deepseek-flash（DeepSeek-V4.1-Flash）¥0.02¥1¥4
deepseek-v4-pro（DeepSeek-V4-Pro-0813）¥0.15¥4.5¥13.5
  • 高峰时段 = 北京时间 周一至周五 9:00–12:00、14:00–18:00，且不含中国法定节假日； 其余时段（含周末与法定节假日全天）均为空闲时段。
  • 节假日表目前同时包含 2026 年官方安排与 2027 年预置日期；2027 年数据应在官方安排发布后复核更新，具体以 src/model-prices.js 为准。
  • 四个计费桶互不重叠：计费输入 = 未命中 + 缓存命中 + 缓存写入。 DSH 的 inputTokens 只表示未命中部分，所以三个桶分别计价再相加。
  • 缓存写入（cacheWriteTokens）DeepSeek 目前恒为 0；若出现，默认按未命中价计费。

已知精度边界：投影基线（开场快照里的累计值）无法拆出逐时明细，只能整体按 快照时刻的峰谷档位计价。它覆盖的是「桥接启动前 + 快照窗口外」的历史， 因此当会话跨过高峰/空闲边界时，这部分金额可能有 ±2 倍以内的偏差。 桥接运行期间逐条采样的金额是精确的。

五、控制台 API

五个端点都在 /api/tokens/*，仅控制台可用：带 x-agent-token 的请求一律 403 （路径刻意放在 /api/socialV2/ 之外，那个前缀对 QQ 侧 AI 是放行的；跨群花费属于管理信息， 不应让某个群的 AI 读到别的群烧了多少钱）。

方法路径说明
GET/api/tokens/summary?limit=200全局合计 + 每个会话一行 + 当前价目表
GET/api/tokens/series?hours=24走势图分桶数据（hours 1~2160；桶数上限 48，可用 buckets 覆盖）
GET/api/tokens/turns?key=group:123&limit=200单个会话的逐轮明细
GET/api/tokens/recent?limit=40最近采样流水
POST/api/tokens/reset清空账本（不可恢复）

summary 的 totals 关键字段：

字段含义
cost总花费（权威值：基线 + 基线之后的逐条增量）
attributedCost其中能归属到具体某一轮的部分
unattributedCost差额：只剩累计值、无法再拆到某一轮的历史花费
byTier.peak / byTier.off高峰期 / 空闲期各自的花费
cacheHitRate缓存命中输入 ÷ 总输入
estimated为 true 表示存在未登记模型，按兜底价估算

七、存储与体量

  • 账本文件：state/token-usage.jsonl，两种行（k:"base" 投影基线 / k:"turn" 逐轮采样）。
  • 行数超过 20000 时自动压缩重写：按内存态去重、丢弃被覆盖的旧采样。每次采样约 200 字节， 压缩后一条会话一轮 ≈ 10 行，正常运行远达不到上限。
  • 进程中断留下的半行会被跳过，不会让整个账本读不出来。
  • 清空账本后，下一次同步会从 DSH 重新拉回各会话的累计值（但逐轮明细只能重新累积）。

八、测试

npm run test:tokens        # 账本 + 价目表单元测试（峰谷判定、幂等折叠、基线合并、压缩、容错）
npm run test:console-ui    # 离线浏览器回归（含「令牌与花费」页渲染与下钻）

单元测试覆盖的语义（每一条都对应一个真踩过的坑）：

  • 峰谷判定按北京时间，且排除法定节假日；
  • 四个桶互不重叠、金额 = Σ(桶 × 单价)；
  • 未知模型兜底并标 estimated；
  • 同一 (turn, step, retry) 后到覆盖先到而不是累加；
  • 重连重放同一批快照不会让用量翻倍；
  • 旧 seq 的采样不得覆盖新数据（否则花费凭空缩水）；
  • llm/retry-started 之后同一步骤的第二次请求另算一次；
  • 权威总量 = 投影基线 + 基线之后 seq 的增量；
  • 逐轮明细与「未逐轮归属」差额自洽；
  • 半行容错、超限压缩后不丢数据（淘汰明细但累计总量精确）；
  • 走势分桶：空桶补零、桶边界对齐（刷新之间不抖）、桶的峰谷档位、 各桶之和 = 窗口合计、更大窗口用更粗的桶且桶数始终受上限约束。
