隐私扫描

本项目会接触真实 QQ 号、群号、本机路径、令牌和聊天内容。误提交后，敏感信息可能长期保留在 公开 Git 历史及已有克隆、fork 中。发布前扫描是必要步骤，扫描结果仍需人工判读，不能机械忽略。

一、运行扫描

node scripts/privacy-scan.mjs                # 扫描已跟踪文件和未忽略的新文件（推荐）
node scripts/privacy-scan.mjs --tracked-only # 只扫描 Git 已跟踪文件
node scripts/privacy-scan.mjs --history      # 追加扫描全部 Git 历史（发布前运行）
node scripts/privacy-scan.mjs --json         # 机读输出

也可以使用：

npm run privacy-scan
npm run privacy-scan:history
  • --history 需要完整克隆；浅克隆可先运行 git fetch --unshallow。
  • 历史扫描按历史 blob 检查，同一内容不会因出现在多个提交中而重复报告。
  • 当前已知历史问题为 15 处旧提交中的本机路径；具体文件和提交以扫描输出为准， 不再只是早期某一篇文档。
  • 当前工作树扫描通过不代表历史干净，普通修复提交也不会消除历史命中。

退出码：0 = 未发现命中，1 = 有命中，2 = 规则或扫描目录等执行错误。

扫描器通常读取 git ls-files 和未被忽略的未跟踪文件；Git 不可用时退化为目录遍历， 并跳过 junction / symlink，避免递归进入仓库外目录。

二、内置规则

规则说明
本机绝对路径例如 Windows 用户目录和其他工作盘路径
QQ 号 / 群号识别常见真实账号长度；文档占位符与测试夹具按规则排除
高熵串检查疑似令牌，同时降低 Git SHA、环境变量名和文件名等误报
凭据赋值检查 accessToken 等字段后的实际值，不把空值或键名当作泄漏
私钥与带凭据 URL检查私钥头和 https://user:pass@host 等形式
不应入库的文件包括 config.json、state/、audio/、日志和备份文件

三、命中后怎么处理

情况处理
真实账号、路径、令牌或聊天内容删除或替换为占位符；凭据应立即轮换，不能只改显示文本
文件本就不应入库从版本控制移除并加入 .gitignore；已经提交过的，继续评估历史处置
脱敏模板、测试夹具或文档示例的误报先核实内容，再添加精确豁免，不要直接关闭整条规则

本地规则文件

模板为 privacy-rules.example.json。复制为 scripts/privacy-rules.json 后填写本机真实标识；该文件必须保持被 .gitignore 排除。 本地规则会与内置默认规则一起使用。

{
  "deny": [
    { "name": "我的真实群号", "pattern": "1001[0-9]{6}", "flags": "" }
  ],
  "denyFiles": ["notes/", "*.private.md"],
  "allowPaths": ["docs/guides/VOICE.md", "scripts/console-ui-"]
}

allowPaths 支持前缀或 * 通配。它是已核实内容的误报豁免，不表示该文件以后无需检查。

四、敏感信息已经提交或公开

情况建议
尚未提交从工作区和暂存区移除敏感内容，再重新检查
已提交但未推送回退相应提交并清理内容；保留需要的非敏感修改
已推送或可能已被克隆 / fork先轮换全部相关凭据，再评估历史清理、协作者通知和必要的重新发布方案

历史重写会影响所有已有克隆、分支和 fork，需要单独制定协调方案。不要认为删除最新提交、 重发 release 或简单 force push 就能撤销已经发生的泄露。

五、CI 用法

- name: Privacy scan
  run: node scripts/privacy-scan.mjs --tracked-only

CI 只扫描当前 checkout 的已跟踪文件。历史扫描需要完整克隆且耗时更长，作为发布前人工检查， 不替代工作树扫描，也不要求通过改写历史来“刷绿”。
