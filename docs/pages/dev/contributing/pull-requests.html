提交 PR

4. 提交 PR

一个 PR 只做一件事。 把 12 个不相关的修复塞进一个 PR，评审成本会高到没人看得完。 PR 的目标分支是 dev（见第 5 节的分支模型）；main 只在发布时从 dev 合并。

PR 里请写清楚：

  1. 改了什么、为什么（贴 issue 号更好）；
  2. 怎么验证的——贴 npm run test:audit 最后那行 Audit suite: N/N scripts passed.；
  3. 有没有行为变更（配置项、工具名、端点、默认值）；有的话同步改 README / docs/。

新增行为请带回归脚本，并把它加进 scripts/test-audit.mjs 的清单——不加进去的测试等于不存在， 因为没人会记得手动跑它。

不要提交：真实 QQ 号 / 群号 / 昵称、任何 token 或密钥、本机绝对路径、state/、node_modules/。 privacy-scan 会拦一部分，但它不是万能网。

5. 维护者的合并方式（据实说明）

本仓库分两条线：main 是正式发布线，只收经过验证的版本；dev 是测试 / 开发线， 持续更新、随时提交，正常状态下领先 main。发布时才把 dev 合入 main，所以两条线可能 短暂同步，但 dev 不应落后于 main。由此：

  • 维护者的日常改动直接提交到 dev；
  • 外部贡献者的 PR 一律以 dev 为目标分支（提向 main 的 PR 会被改指向 dev）；
  • 你的 PR 可能直接合并，也可能被参考后重新实现，还可能在 dev 里已经修好了；
  • 以上三种情况都会在 PR 里回复说明，不会让你干等；
  • 如果 dev 里已包含等价修复，维护者会指出对应的提交并关闭 PR——这不代表你的工作没价值， 通常只是两条线同时撞上了同一个问题。

想用正式发布版就待在 main（git clone 默认拿到的就是它）；想跟最新改动就切到 dev （测试线，不保证稳定）。

6. 许可

提交 PR 即表示你同意你的贡献按本仓库的 PolyForm Noncommercial 1.0.0 发布（许可范围与第三方组件声明见 NOTICE.md）。

如果你不能接受这一点（例如你的雇主对该代码有 CLA 或再许可要求），请先开 issue 讨论， 不要直接提 PR。

五、改动检查单（每个 PR 自问）

  1. 这次改动有没有让某个"不确定"变成"放行"？（违反 fail-closed 即阻断）
  2. 有没有新增一个只有控制台该用的端点却没进 agent 白名单的默认拒绝？
  3. 有没有新增读写文件的路径参数？它是否做了包含性校验与 realpath？
  4. 有没有把外部数据（QQ 内容、文件名、配置值）直接插进 HTML / 日志 / 提示词？
  5. 新增的定时器、Map/Set、监听器，在会话退役与进程退出路径上都清理了吗？
  6. 是否更新了对应的测试与本文档？
