常见问题

常见问题

  • 启动时先出现「连接断开（1006）」随后恢复：部分 SnowLuma 部署会为 HTTP 与 WS 使用不同令牌，而 config.json 的 snowluma.accessToken 只显式保存一个值。首次 WS 连接可能因此失败，再由桥接从 snowluma.homeDir 的 config/onebot_<QQ号>.json 发现对应令牌并重连。仅在这条自愈链路成功时，短暂 1006 属于预期现象；如果持续失败或收不到消息，则需检查令牌和 homeDir，不能一概视为正常。
  • QQ 上毫无反应，但桥接日志说「SnowLuma 已连接」：已连接只表示 WebSocket 建立，不能证明 QQ 数据链路正常，可能是上游接入层（SnowLuma 的 [Hook]）未收到数据，也可能是桥接配置或会话路由问题，应按以下顺序排查。
    1. 打开控制台「运行总览」，看 SnowLuma 上游 卡片：已连接 · 未接收 表示连接存在但未收到上游数据；「访问与安全」页会有对应告警条与处置建议。GET /api/status 的 snowluma 字段（degraded / good / hint）给的是同一份判断。
    2. 去看 SnowLuma 自己的接入日志 logs/snowluma-*.log，搜 [Hook]（以下均为 SnowLuma 日志字段）：
      • receive path stale: … reporting good=false —— 日志：收不到数据（会自愈，也可能不自愈）
      • process enumeration timed out after 4000ms —— 日志：连 QQ 进程都枚举不到
      • 正常应有 login detected: PID=… + pipe connected: PID=… —— 日志字段
    3. 再核对白名单、DSH 会话与桥接日志，排除本项目的配置问题。是否升级 SnowLuma 应根据其发布说明判断；本项目只读取本机接入配置与上游健康状态，不部署、不修改上游本体。历史核验仅证明 1.14.9 与 1.14.20 的原生组件相同，因此那次版本升级不能修复原生 hook 挂载问题，不能推广为所有版本的结论（见 DSH 0.2.0 适配记录）。
    4. 顺带确认 QQ 客户端本身是登录状态、没有被顶号；SnowLuma 1.14.20 已验证会通过 bot_status 事件报告账号上下线，桥接日志会记录「QQ 账号会话已离线」。

    桥接自身不包含原生注入组件，也不启动或控制 SnowLuma / QQ；遇到上游接入失败应先检查 SnowLuma 日志，而不是直接归因于桥接。

  • 看不到 qq-mode 设置卡片：这是已知限制，不是配置错误。DSH 的 settings.plugin.item 槽位只渲染「host 已注册的命名空间 ∩ 声明了该 key 的卡片」，而卡片必须由插件的浏览器半（package.json 的 dsh.client + lib/client.js）注册；plugins/qq-mode-console 目前只有 host 半。反复重跑 setup-dsh.mjs 或重启 DSH 都不会让卡片出现。要真正修好需补一个 lib/client.js。
  • 改了模式却不生效 / 5 秒后被改回去：此问题已在 src/bridge.js 修复（桥接需重启后生效）。历史成因：refreshMode() 每 5 秒被 checkDsh 调用一次，先读 DSH 的 qq-mode 命名空间，只要有合法值就直接 return，完全忽略本地 state/mode.json；而命名空间的默认值始终存在，所以 DSH 侧永远有值 —— 于是控制台写本地文件会在下一次轮询被覆盖回滚。现在 POST /api/mode 会写穿到 DSH 设置（api.settings.update({ ns: 'qq-mode', patch: { mode } })），响应里新增 dshSynced 字段；若写穿失败（DSH 未运行等）会记日志并保留本地值。注意 settings/update 在 0.2.0 是多参数 RPC：args 是 { ns, patch, expectedRevision } 平铺，不是 { request: {...} }（传 request 会被网关拒为 gateway/arguments-invalid）。同源问题：closedAgentPreset 在 DSH schema 里不存在，原先也因这个提前 return 而失效，现已改为始终以本地 state/mode.json 为准。若仍看到回滚，检查桥接日志里是否有「写穿 DSH 设置失败」。
  • MCP 工具没有出现：确认 cordis.patch.yml 中三个 MCP 条目的路径指向当前仓库，并重启 DSH。
  • preset 没有出现：DSH 0.1.7 起 preset 不再是 ~/.dsh/.agent-presets/<名>/ 目录（该目录完全不被读取）。preset 现在是 profile 里的一条 @deepseek-ai/dsh-agent-preset 行，由 plugins/qq-agent-presets 这个 bundle 提供。检查 profile 的 package.json 的 dsh.profile.bundles 是否含 qq-agent-presets、dependencies 是否有对应的 link:，以及 ~/.dsh/profiles/web/node_modules/qq-agent-presets 链接是否存在；缺了就重跑 node scripts/setup-dsh.mjs 再重启 DSH。桥接里可用 npm run probe:protocol / npm run verify:adaptation 确认 agentPresets/list 里能看到 qq-chat、qq-chat-v2。
  • 安装完成但 RPC 看不到预设或设置：先对照安装脚本与运行中的 DSH/桥接是否使用相同用户、DSH_HOME 和 profile。终端里的 --dump-config 只证明该终端所用配置已合成，不证明后台进程使用同一份配置。#77 的最终讨论已将该次故障定位为运行用户不一致。若同一进程的插件注册表能看到预设，而 RPC 仍看不到，需保留安装形态和最小诊断继续定位 DSH 作用域问题（#97）；不能回退到完整工具预设绕过检查。
  • Cannot find package 'js-yaml' 等依赖缺失：Release 源码包不包含 node_modules。在解压后的仓库根目录运行 npm install，确认成功后再启动；不要跳过 postinstall。package.json 和锁文件已声明 js-yaml（#91）。
  • 网页、搜索或图片因 fake-ip 被拦截：Clash/mihomo 的 fake-ip 可能把域名映射到 198.18.0.0/15，该段仍属于禁止访问的保留地址。可按 mihomo DNS 官方文档切换 enhanced-mode: redir-host，或在 fake-ip-filter-mode: blacklist 时让受影响的公网域名命中 fake-ip-filter，使其返回真实地址；修改后清理代理及系统 DNS 缓存再试。桥接仍会校验真实解析结果，不提供跳过私有地址检查的开关（#40、#111）。
  • 启动 DSH 报 failed to parse overlay cordis.patch.yml: YAMLException：多为历史版脚本残留的空数组 [] 引发。重新运行最新版脚本（会自动剥离）即可，或手动删除该文件里独立成行的 [] 后重启 DSH。
  • 启动 DSH 报 cannot resolve profile bundle "qq-mode-console"：profile 的 bundle 依赖尚未安装。运行 dsh plugin --profile web install（web 换成你的实际 profile 名）后重启 DSH；新版脚本会尝试自动执行这一步。
  • 启动 DSH 报 failed to apply loader entry persona (@deepseek-ai/dsh-persona): invalid config: $.prefix missing required value：preset 的 persona 段缺少 prefix。DSH 0.1.5 起 dsh-persona 只接受 prefix / suffix / complete / includeRuntimeContext，而旧写法用的是 text —— schemastery 的 z.object 非 strict，未知键会被静默忽略，于是真正报出来的是「缺 prefix」（不是「text 这个键被拒绝」）。重新运行 node scripts/setup-dsh.mjs（本仓库 preset 已改为 prefix），或手动把 preset 里的 text: 改成 prefix:。可用 node scripts/verify-persona-config.mjs 提前自检。
  • profile 的 bundle 条目被重置：升级 DSH 可能重置 ~/.dsh/profiles/web/package.json，把 qq-mode-console 的依赖与 bundle 条目删掉（症状是启动报 cannot resolve profile bundle，或桥接读不到 qq-mode 设置值）。重新运行 node scripts/setup-dsh.mjs，再跑 dsh plugin --profile web install 并重启 DSH。
  • QQ preset 挂载失败，群里 AI 完全没反应：chat / reserved / reserved2（会话可能属于 QQ 群）必须挂上 qq-chat / qq-chat-v2，否则桥接直接拒绝建会话并打日志 ⛔ 群聊/仿真会话缺少 preset …——QQ 上表现为「发了消息没人回」，而桥接日志里能查到原因。这是有意的 fail-closed 设计：「无 preset 会话」= DSH 默认 preset（通常 standard，含 bash/文件读写），降级过去等于把本地工具暴露给群里的任何人。closed-agent 模式（仅 owner 私聊）是唯一例外，那里本就使用完整工具面，允许回落。修复：确认 plugins/qq-agent-presets bundle 已注册进 profile（bundles + link: 依赖 + node_modules junction 三者齐备，跑 node scripts/setup-dsh.mjs 可自动补齐）并重启 DSH；若手改过 config.json 的 agentPreset，确认该名字确实在 DSH 的 preset 清单里。
  • 发送消息报 unauthorized / HTTP 401：先分别核对 SnowLuma HTTP 与 WebSocket 的令牌、地址和实际使用账号。HTTP 与 WS 可以使用不同令牌，不要求强制设为相同；确保 snowluma.accessToken 与 HTTP API 匹配，并确认 snowluma.homeDir 能让桥接发现 WS 所需的对应令牌，然后重启桥接。
  • DSH 侧 401/鉴权失败：DSH 0.1.7 起进程启动 token 是每进程现生成、只存在内存的随机数（不落盘、不可推导），旧版「从 ~/.dsh/guard/logs/server-*.out.log 里读 token」的办法已经失效（读到的是上一个进程的陈旧 token，换 Cookie 只会 401）。桥接现在默认离线铸造 Cookie：读 ~/.dsh/.credentials.yaml 里持久化的 client-connection/browser-session 签名密钥自签一个会话 Cookie，不依赖任何进程期状态。config.json 的 dsh.authToken 一般应留空；只有显式填了才会优先走 token 交换。若报鉴权失败，先确认 DSH_HOME 指向真正的 .dsh 目录、且该文件里有 client-connection/browser-session 记录。npm run test:dsh-auth（17 项断言）与 npm run self-test 可快速定位。
  • 发送消息报 HTTP 426（Upgrade Required）：说明 config.json 里的 snowluma.httpUrl 指向了 WebSocket 端口。httpUrl 必须是 OneBot 的 HTTP API 地址（例如 http://127.0.0.1:3000），而 wsUrl 才是 WebSocket 地址（例如 ws://127.0.0.1:3001）。请在 SnowLuma WebUI 的 OneBot 配置里分别确认 HTTP 和 WebSocket 的端口。也可以运行诊断脚本： 
    node scripts/check-onebot-status.mjs
