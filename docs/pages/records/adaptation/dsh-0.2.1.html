DSH 0.2.1 适配记录（qq-bridge v0.2.1-r1）

本文的边界：只记录为适配 DSH 0.2.1-rc.2 而做的改动。每一条给出四件事： 现象 / 为什么必须改 / 证据 / 怎么验证。

复核后判定兼容、因此没改的部分在 §4 —— "没改"同样是结论。

适配目标：@deepseek-ai/dsh 0.2.1-rc.2（上一版适配目标 0.2.0-rc.2， 记录见 DSH_020_ADAPTATION.md）。本文写于 2026-10-22。

上游行为标注：文中“协议层/线协议/实测”等指 DSH API 的兼容性验证；“本机签名密钥/Cookie 生成”等指 qq-bridge 自身的本机鉴权行为，不是 SnowLuma 或 DSH 的机制。

版本身份：桥接 v0.2.1-r1（版本号方案见 DSH_020 附录 H：主版本与 DSH 同步， r1 = 0.2.1 线第 1 次发布）。不用裸 v0.2.1 是因为历史上那次被撤回的标签 已经用过这个名字（commit 9bb7b98 仍在历史里），重名只会让标签列表更难解释。

0. 一句话结论

协议面零漂移，但有两处真实断裂，第一处会让 QQ 侧完全不回：

级别问题影响
P0提示词变量 {{cwd}} 在 0.2.1 被删除（agent loop 现在只注册 provider / model）两个 QQ preset 的每一次回合都在 turn/start 后立刻 error，模型一次都不跑 ⇒ QQ 上表现为「发消息完全没反应」，且日志里只有一行 error
P1dsh-base 新增默认挂载 working-directory，全局层多出 working_directory 工具QQ 仿真会话的 schema 会继承它（L7 的"注册期不得含本地能力"被破坏）；执行期白名单仍会拒绝调用

外加两族"潜在口子"（terminal / session-query / plugin_market）已列进守卫回归网； Codex / Claude Code 改为按需安装，两个老工具名改判为「可选项」。

业务逻辑（bridge.js）一行没动，改动全部落在 preset persona 文本 + 守卫名单 + 对账脚本。

2. 断裂点一（P0）：{{cwd}} 变量被删除 ⇒ 每一回合直接 error

2.1 现象

用 qq-chat-v2 建一个会话、发一句普通 prompt，事件流里只有：

turn/start {"turn":1}
turn/end   {"turn":1,"reason":{"kind":"error","error":{
             "message":"unknown prompt variable \"{{cwd}}\" in section \"deployment:persona-suffix\";
                        registered variables: provider, model","code":"UNKNOWN"}},"text":""}

没有 assistant/message、没有 tool/call——模型根本没被调用。 QQ 侧的现象就是"发消息没反应"，而桥接日志里只有一行 AI 内部输出：...（空）。

2.2 为什么必须改

  • dsh-agent-loop 在 0.2.1 只注册两个提示词变量： 
    ctx.systemPrompt.variable("provider", ...);
ctx.systemPrompt.variable("model", ...);

    0.2.0 还有 cwd，0.2.1 把它删了。

  • dsh-system-prompt 对未知变量是 fail loud（不是渲染成空串）： interpolate() 直接 throw new Error('unknown prompt variable ...')。
  • 于是两个 preset 的 persona suffix Your working directory is {{cwd}}. 让每一次 系统提示词装配都抛错。这不是"少一条信息"，是整条对话链 100% 不可用。
  • 工作目录并没有丢：0.2.1 新增的 dsh-working-directory 会以 working-directory:current 的运行时上下文（required: true、interpolate: false） 提供当前目录，persona 的 includeRuntimeContext 默认 true，模型照样看得到。

2.3 改法

删掉两个 preset 的 persona suffix（并在注释里写明为什么不能再写 {{cwd}}）：

  • dsh/agent-presets/qq-chat/agent.cordis.yml
  • dsh/agent-presets/qq-chat-v2/agent.cordis.yml

然后 node scripts/build-agent-preset-patches.mjs 重新生成 plugins/qq-agent-presets/presets/*.patch.yml（产物是纯生成物，不许手改）。

好消息：preset 文本的改动不需要重启 DSH——新建/恢复会话时按当前 patch 解析， 实测改完立刻生效（见 §5 的活体回合与工具调用）。

2.4 怎么验证

  1. 静态：verify:adaptation 里的「只引用 DSH 已注册的提示词变量」—— 拿 persona 配置里出现的所有 {{var}} 与 {provider, model} 求差，不只看有没有 {{model}}。 verify-persona-config.mjs 同样改成了这个口径。
  2. 活体（本轮新增，这就是当初该有的那条网）： verify:adaptation §5g 真建一个 qq-chat-v2 会话、发一句 prompt、等 turn/end， 断言 reason.kind === 'completed' 且文本非空。静态断言只能看出"写了什么变量"， 只有真跑一回合才能证明它可解析。
  3. 端到端：node scripts/probe-tools.mjs qq-chat-v2 → MCP 工具可调用、未调用本地工具。

3. 断裂点二（P1）：working_directory 进了仿真会话

3.1 证据

state/tool-restrict.log（升级重启后第一轮 preset apply）里 known global tools 从 3 个变 4 个：

restrict ok=3 failed=64 原因: tools.restrict() names unknown global tool "pwsh";
known global tools: list_mcp_resource_templates, list_mcp_resources, read_mcp_resource, working_directory

来源可查：dsh-base/cordis.patch.yml 现在无条件挂载两行：

- id: working-directory
  name: '@deepseek-ai/dsh-working-directory'
- id: tool-working-directory
  name: '@deepseek-ai/dsh-tool-working-directory'

3.2 为什么这是安全问题而不是清洁问题

L7 要求仿真会话的 preset 注册期就不得含本地能力。tools.guard 只在执行期拒绝， 工具名仍留在模型 schema 里——既违反注册期要求，也会诱导模型去调它。 working_directory 能改写会话工作目录，属于"本地环境状态"，不是 QQ 动作面能力。

执行期白名单这一层没有失效：working_directory 不在 SAFE_EXACT / MCP 前缀里， 调用照样被拒。这是"第二层兜住了"，不是"没问题"。

3.4 改法

  1. plugins/qq-agent-presets/qq-tool-restrict.mjs：LOCAL_EXECUTION_TOOLS 增 13 个名字； 新增导出 OPTIONAL_BUNDLE_TOOL_NAMES = ['subagent_codex','subagent_claude_code'] （0.2.1 把 Codex / Claude Code 改成按需安装，默认扫不到；仍进名单，装上就挡）。
  2. scripts/scan-dsh-tool-names.mjs：假名判定排除可选组，并在输出里点名说明。
  3. scripts/verify-dsh-021-adaptation.mjs：新增 GUARD_021_NAMES 断言。
  4. scripts/test-preset-local-tools.mjs：本地执行工具清单同步补齐（restrict 覆盖 + 执行期拒绝两条断言）。

3.5 怎么验证

node scripts/scan-dsh-tool-names.mjs --missing   # 悬空 0，未覆盖危险名 0
node scripts/test-preset-local-tools.mjs         # 7/7
node scripts/verify-dsh-021-adaptation.mjs       # 75 通过 0 失败

守卫是 preset 行 import 的模块，运行中的 DSH 按 URL 缓存；已经开着的会话仍用旧名单， 新建会话才用新名单。彻底生效（含既有会话）重启一次 dsh web 即可，确认信号： state/tool-restrict.log 里 restrict ok=3 → ok=4，且失败样例里不再有全局工具。
